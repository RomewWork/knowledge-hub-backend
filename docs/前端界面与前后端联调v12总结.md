# 前端界面与前后端联调 v12 总结

> 课程 60 · 前端 `knowledge-hub-frontend`（v12）· 后端 `knowledge-hub-backend`（origin/v12）
> 整理时间：2026-11-06

## 一句话

**前 11 讲把能力做进后端，v12 把它们接成一个人能用的产品**：一个壳（AppLayout）+ 13 个页面 + 一层统一请求封装，把登录态、三级权限、文档生命周期、检索/图谱/问答全部打通。

> 本讲的重点不是"画页面"，而是**对齐两套系统的契约**：路径前缀、鉴权头、401 刷新、错误格式、字段命名。

## 联调四根支柱

### 1. 前缀：`/api` 只存在于前端

```ts
// vite.config.ts
server: {
  port: 5173,
  proxy: {
    '/api': {
      target: 'http://localhost:3000',
      changeOrigin: true,
      rewrite: (path) => path.replace(/^\/api/, ''),
    },
  },
}
```

前端写 `/api/documents` → 转发到 `http://localhost:3000/documents`。
后端 `main.ts` **没有** `setGlobalPrefix`，所以两边约定：**前端统一带 `/api`，后端统一不带**。

### 2. CORS 与 ValidationPipe（v12 新增）

```ts
const app = await NestFactory.create(AppModule);
app.enableCors({ origin: true, credentials: true });   // v12 新增
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,              // 剥离 DTO 未声明字段
    transform: true,              // 字符串 → number 等
    forbidNonWhitelisted: true,   // 多传字段直接 400
  }),
);
await app.listen(process.env.PORT ?? 3000);
```

`origin: true` 回显来源（`credentials: true` 时不能用 `*`）。

### 3. 鉴权：统一注入 + 401 单飞刷新

`src/api/client.ts`：

```
request(path, init, retry)
 ├─ FormData → 不设 Content-Type（浏览器自带 boundary）
 ├─ JSON   → 自动 Content-Type: application/json
 ├─ 有 token → Authorization: Bearer
 ├─ 401 且非 login/refresh 且 retry → tryRefresh()
 │    ├─ 成功 → 重放（retry=false，防死循环）
 │    └─ 失败 → clearAuth() + 抛 401
 └─ 非 2xx → ApiError(status, 归一后的 message)
```

`tryRefresh` 用 **`refreshing` 单例 Promise**：并发多个 401 只发一次 refresh，其余等同一个 Promise。

token 存储：`localStorage` 的 `kh_access_token` / `kh_refresh_token` / `kh_user`，通过 `useSyncExternalStore` 暴露（`src/auth.ts`），避免 Context 全局重渲染。

### 4. 契约层：页面不直接 fetch

`src/api/index.ts` 按领域拆成 9 个对象：

```
authApi / documentApi / searchApi / aiApi / graphApi
userApi / roleApi / permissionApi / teamApi
```

页面只调 `aiApi.chat(...)`，路径与返回类型集中在 `src/types.ts`。**后端改字段只改这一层。**

## 菜单级权限（前端真实实现）

`AppLayout` 里菜单项由用户能力动态拼装：

```ts
if (can(user, 'document:list')) items.push({ key: '/documents', ... })
if (can(user, 'search')) {
  items.push({ key: '/search' }, { key: '/chat' }, { key: '/graph' })
}
if (can(user, 'profile')) items.push({ key: '/profile' })
if (isAdmin(user)) items.push({ key: '/admin/users' })
```

侧栏里，审核工作台额外用 `isReviewer(user)` 控制。

> 这只是**体验层**：隐藏菜单不等于安全，后端 `@RequirePermission` 才是边界。

## 后端 v12 的两处改动

### ① 启动装配

CORS + `ValidationPipe`（见上文）。

### ② 图谱全景接口

```ts
@Controller('graph')
@RequirePermission(PermissionCode.search)   // 类级：整个图谱查询要 search 权限
export class GraphController {
  /** 全景：文档 / 实体 / 标签 + 统计，供前端力导向图 */
  @Get('overview')
  overview(@Query() query: GraphOverviewDto) { ... }
}
```

`GraphOverviewDto`：`keyword? / entityType? / from? / to? / docLimit?`（**上限 80**，`from`/`to` 按文档 `updatedAt` 过滤）。

`graph-build.service.ts` 配套 +319 行实现 `getOverview()`，把「文档 + 实体 + 标签 + 统计」**一次聚合**返回。

> 为什么不在前端逐节点查？力导向图要一次拿全节点和边才能布局，N 次请求会让图"边加载边抖动"。

## 文档生命周期联调

```
新建（草稿）→ 编辑 → 发布/提审 → 审核通过/驳回 → 已发布 ⇄ 归档
                                   ↑
上传解析（/documents/upload/parse，FormData）
```

两个易混点：
- **上传解析**和**新建文档**是两条并列记录，各自独立状态；
- 前端隐藏「发布」按钮 ≠ 不能发布，后端仍按状态机校验（`canPublishFrom`）。

## 易错点

| 坑 | 说明 |
|---|---|
| `/api` 前缀 | 前端必须带、后端不能有；`VITE_API_BASE` 改错 → 全站 404 |
| 401 死循环 | `login`/`refresh` 自身不重试（代码已排除这两个路径） |
| 并发刷新 | 必须单例 Promise，否则 N 个 401 触发 N 次 refresh |
| FormData | 别手动设 `Content-Type`，否则 boundary 丢失 |
| CORS + credentials | `origin` 不能写 `*`，要 `origin: true` 回显 |
| `forbidNonWhitelisted: true` | 前端多传一个未声明字段就 400，联调时容易误判「接口挂了」 |
| 菜单权限≠安全 | 前端隐藏只是体验，后端必须再校验一次 |
| `docLimit` 上限 80 | 超了直接 400 |
| localStorage 存 token | 有 XSS 风险；生产建议 httpOnly cookie + CSRF |

## 验收

| 检查点 | 期望 |
|---|---|
| 登录后刷新页面 | 仍保持登录（localStorage 恢复） |
| access 过期后操作 | 自动刷新并重放，用户无感 |
| refresh 也过期 | 跳登录页（`clearAuth`） |
| 上传文档 | Network 里是 `multipart/form-data`，无手动 Content-Type |
| 搜索页 | 命中词高亮（后端 `<em>`） |
| 对话页 | 答案带 `[1]`，点击定位到来源卡片 |
| 图谱页 | 一次 `/api/graph/overview` 拿全景，图不抖动 |
| 普通用户直接访问 `/admin/users` | 菜单不显示；改 URL 进入后被后端 403 |
| 多标签页同时过期 | 只发一次 refresh（Network 可见） |

## 主动回忆

1. **为什么 `/api` 前缀只在前端存在？**
   Vite 代理负责剥离；后端没有 global prefix，接口路径就是 controller 上的路径。两边各管一段，前端统一带、后端统一不带，避免"到底谁加前缀"的混乱。

2. **401 刷新为什么要单例 Promise？**
   页面同时发 5 个请求，token 都过期 → 5 个 401 → 若各自 refresh，会用同一个 refresh token 发 5 次，可能触发服务端轮换策略把彼此作废。单例让它们共享一次刷新结果。

3. **前端隐藏按钮够不够？**
   不够。前端只控制"看不看得见"，任何人都能改 JS 或直接发请求；接口必须用 `@RequirePermission` 再校验一次。两层缺一不可。

4. **为什么图谱要新开 `/graph/overview`？**
   力导向图需要节点 + 边 + 统计一次性到位才能布局；复用 `/graph/nodes` + `/graph/edges` 会多请求、且两次结果可能不一致（中间有写入）。

5. **这一讲为什么前端先做、后端只改两处？**
   因为前 11 讲已把能力（鉴权、检索、图谱、RAG）都做完了，v12 只是"消费"它们。后端唯一缺口是 CORS 和图谱全景聚合——**联调暴露的是契约缺口，不是功能缺口**。
