# 文档模块 v2 总结（多格式文件 → Markdown + 对象存储）

> 对应课程：50 多格式文件转 Markdown（配合 38 对象存储方案）
> 代码基线：`ai-agent-code/knowledge/knowledge-hub-backend`（学习项目，v2 已完成，尚未提交）
> 技术栈：Nest 12 + pdf-parse 2 + mammoth + turndown(+gfm) + exceljs + jszip + officeparser + @aws-sdk/client-s3
> 整理时间：2026-10-24

---

## 0. 一页速览

v2 只做一件事：**让「上传一个文件」变成「得到一篇结构化 Markdown」，并把原文件与图片落到对象存储。**

| 维度 | 结论 |
| --- | --- |
| 入口 | `POST /documents/upload/parse`，`multipart/form-data`，字段名 **`file`**，上限 50MB（`FileInterceptor`） |
| 支持格式 | `pdf / docx / xlsx / pptx / txt / md`（大小写不敏感） |
| 分发 | `FileParserService.parse()` 按扩展名 `switch`，每个格式一个纯函数 parser |
| 统一出口 | **Markdown 字符串**，图片以 `![](url)` 内联，表格以 GFM 表格内联 |
| 原文件 | 上传 RustFS（S3 兼容），key 形如 `documents/2026/10/24/文件名-uuid.ext`，返回公网 URL |
| 图片 | PDF 抽取的图片走 `pdf-images/` 前缀；单张失败只跳过该张 |
| 落库 | 复用 v1 的 `create()`：正文进 Mongo，元数据进 PG，状态固定 `Draft(0)` |
| 降级 | pptx：自研 ZIP → officeparser；xlsx：exceljs → officeparser；pdf 图片失败 → 纯文本 |
| 失败口径 | 解析结果为空 → `400`，**拒绝入库**（不存空文档） |
| 未落地 | 异步流水线、分块、向量化、ES/图索引、状态机审核、鉴权 |

```
POST /documents/upload/parse
   │  multer(memoryStorage) → file.buffer / originalname / mimetype / size
   ▼
DocumentController.uploadAndParse
   │  无文件 → 400
   ▼
DocumentService.uploadAndCreateDocument(file, meta)
   │  ① decodeUploadFilename   中文名 Latin-1 → UTF-8 还原
   │  ② getExtension + isSupported
   │  ③ FileParserService.parse → Markdown
   │  ④ RustFS.uploadBytes(原文件) → fileUrl（未启用则跳过）
   │  ⑤ create({ title, content: markdown, status: Draft })
   ▼
{ documentId, title, fileUrl, fileSize, fileExtension, contentLength, contentPreview, status }
```

## 1. 为什么要有「统一层」

v2 真正学到的不是四个库的 API，而是一个分层决策：**入口按格式分化，出口强行统一。**

- **入口不能统一**：OOXML 本质是 ZIP + XML，XLSX 是二维网格，PDF 是绘图指令流，纯文本就是字节。没有任何一个库能同时把这四种结构解析好。
- **出口必须统一**：下游的存储、切分、向量化、全文索引、前端渲染，只愿意处理一种文本格式。

于是 Markdown 成为这个「收口点」：

| 候选出口 | 为什么没选 |
| --- | --- |
| 纯文本 | 丢掉标题层级、表格、列表，切分后语义断裂 |
| HTML | 结构保留但噪音多（style/class/span），体积大，切分要清洗 |
| AST / JSON | 保真度最高，但没有现成存储/渲染/向量化链路，前端还要再解析 |
| **Markdown** | 结构够用、体积小、可 diff、可人工校对、模型友好、图片天然走 URL |

## 2. 五个解析器逐个拆

### 2.0 统一契约

所有 parser 都是**纯函数**，不依赖 Nest 容器、不碰存储、不做 IO：

```ts
(buffer: Buffer) => string            // 同步：plain-text
(buffer: Buffer) => Promise<string>   // 异步：docx / xlsx / pptx / pdf
```

这条约定很重要：parser 可单测、可组合、可在队列里跑。**副作用（上传图片、写库）全部上移到 service 层。**

### 2.1 plain-text（8 行）

```ts
export function parsePlainText(buffer: Buffer): string {
  return buffer.toString('utf8');
}
```

不做任何结构转换。TXT/MD 本身就是目标格式，**反而不能清洗**，否则会改掉用户原文。

### 2.2 docx：mammoth → HTML → turndown → Markdown

```
DOCX ──mammoth──► HTML ──turndown(+gfm)──► Markdown ──cleanMarkdown──► 定稿
```

关键点：

1. **`styleMap` 必须同时覆盖中英文样式名**。中文版 Word 的内置样式叫「标题 1」，不覆盖就全变普通段落：
   ```ts
   "p[style-name='Heading 1'] => h1:fresh",
   "p[style-name='标题 1'] => h1:fresh",
   ```
2. **`turndown.use(gfm)`** 才支持表格 / 删除线 / 任务列表，否则 Word 表格会被压成纯文本。
3. **`headingStyle: 'atx'`**（`#` 而不是下划线）、`bulletListMarker: '-'`。

实测：`梁多强_Agent开发.docx` → **6669 字符**，六大节顺序完整，中文标题层级正确。**docx 是四种格式里质量最高的。**

### 2.3 xlsx：exceljs → Markdown 表格

```
XLSX ──exceljs──► 二维字符串数组 ──toMarkdownTable──► GFM 表格
```

实现细节都值得记：

| 细节 | 代码位置 | 说明 |
| --- | --- | --- |
| Sheet 一表一节 | 每个 Sheet 输出 `## 表名` 作小标题 | 多 Sheet 不丢表名 |
| 稀疏行对齐 | `Math.max(row.actualCellCount, values.length - 1)` | `row.values` 下标从 1 开始，稀疏行尾列会算少 |
| 列数对齐 | 短行右侧补 `''` | 否则 GFM 表格列数不齐，渲染错位 |
| 空 Sheet | 仍输出标题 + 空行 | 保留表名信息 |
| 值归一 | `cellToString()` | 覆盖原始类型 / Date / 公式取 `result` / 超链接取 `text` / 富文本拼 `richText` |

**已知缺陷**：`cellToString` 里 `value instanceof Date` 直接 `toISOString()`，导致日期列全是 `2019-03-01T00:00:00.000Z`。应格式化为 `YYYY-MM-DD`（有分秒才带时间）。见 [§9](#9-v2-踩坑记录真实发生)。

### 2.4 pptx：先自研 ZIP，再 officeparser 兜底

```
PPTX ──jszip──► ppt/slides/slideN.xml（按 N 数字排序，不是字典序！）
        │
        ├─ 每页 `## 幻灯片 N`
        ├─ 表格 → toMarkdownTable；抽出后从 XML 里删掉 <a:tbl> 防止重复
        ├─ title/ctrTitle 占位符 → `### 标题`
        └─ 其余段落 → 正文（已作为标题的文本跳过）
   ↓ 失败
officeparser.parseOffice(fileType:'pptx') → ast.to('md')
```

排序坑：`slide1.xml, slide10.xml, slide2.xml` 按字符串排会乱，必须 `slideNumber()` 取数字比较。

实测：`申论总结课.pptx` → **2812 字符 / 27 页**，与源文件幻灯片数完全一致。

### 2.5 pdf：唯一有真问题的格式

```
PDF ──pdf-parse v2 getText()──► 每页 text
    ──getImage()──────────────► 每页图片 → 上传 RustFS
    ──getTable()──────────────► 表格（正文无 `| ---` 时才追加「检测到的表格」章节）
        ↓
   按页拼装：本页文本 + 本页所有图片
```

两个结构性缺陷：

1. **图片整页堆在页尾**：`parts.push(text)` 之后紧跟所有 `![](url)`，所以「第1页文本 → 4张图 → 第2页文本」，句子看起来被打断，实际是跨页断句 + 图片插入叠加。
2. **多栏版面无法重排**：`pdf-parse` v2 的 `PageTextResult` 只有 `{ num, text }`，**不给文字坐标**。双栏简历会按内容流顺序交错吐出，`教育经历` 标题和 `九江学院` 正文被拆到相隔 37 行。

实测：`李先生_28岁.pdf` → **7746 字符 / 232 行 / 9 张图**，但章节顺序错乱。

> 结论：**这是引擎能力边界，不是写错了代码。** 要修只能换引擎（officeparser 实测顺序正确，或课程 v20 的 MinerU）。

## 3. 分发器与降级策略

`FileParserService` 只干三件事：**校验 → 分发 → 兜底**。

| 策略 | 实现 |
| --- | --- |
| 扩展名白名单 | `SUPPORTED_EXTENSIONS`，大小写不敏感；不支持直接 400 并回显支持列表 |
| 空内容拦截 | `!file.buffer?.length` → 400 |
| 空结果拦截 | `!result?.trim()` → 400，**不写库** |
| xlsx 双重降级 | `parseXlsx` 抛错 → `officeparser` 的 `ast.to('md')` |
| pdf 图片可插拔 | `uploadImage` 回调由 service 注入，未启用 RustFS 时只出文本 |
| 单图失败隔离 | 一张图上传失败只 `logger.warn`，不影响整份文档 |
| 耗时观测 | 每次解析记录 `chars` 与 `elapsed`，是排查「为什么很慢」的第一手数据 |

**设计要点：降级发生在 parser 内部，而不是往上抛给 controller。** 用户不该看到「officeparser 也失败了」这种中间态。

## 4. 对象存储 RustFS（S3 兼容）

为什么邮箱附件式的「存本地磁盘」不行：

| 问题 | 本地盘 | 对象存储 |
| --- | --- | --- |
| 多实例 | 每个 Pod 写自己的盘，读不到别人的 | 共享，天然多实例 |
| 扩容 | 磁盘满就挂 | 几乎无限 |
| 备份 | 自己写脚本 | 桶级生命周期 / 跨区复制 |
| 分发 | 走应用服务器带宽 | 预签名 URL / CDN |
| 数据库 | 存大 BLOB，拖垮主库 | 只存 object key |

实现要点（`rustfs.service.ts`）：

- `onModuleInit` 里建 `S3Client`（`forcePathStyle: true`，S3 兼容服务必开），并**异步** `ensureBucket()`，失败只 warn，首次上传时重试。
- `isEnabled()` 三态判断：配置开关 `RUSTFS_ENABLED` + client 是否建成。**整个上传链路可以整体关闭**，本地开发不需要对象存储也能跑解析。
- key 设计：`{prefix}/{yyyy}/{MM}/{dd}/{安全文件名}-{uuid}{ext}`，`sanitizeBaseName` 保留中文但替换非法字符、截断 64 字符。
- 返回 URL：`{publicBase}/{bucket}/{key}`，不做预签名（演示用；生产应换预签名 + 有效期）。

## 5. 上传解析主链路回顾

```
controller  只做两件事：拦无文件、转交 service
service     编排：文件名还原 → 校验 → 解析 → 传原文件 → 建文档
parser      纯函数：buffer → markdown
storage     纯 IO：bytes → url
```

顺手记三个「容易被忽略但要命」的点：

1. **中文文件名乱码**：multer/busboy 把 UTF-8 文件名字节按 Latin-1 解码，得到 `ç³è®º` 之类。`decodeUploadFilename` 用 `Buffer.from(name,'latin1').toString('utf8')` 还原，解出替换字符则保留原值。
2. **标题来源**：`titleFromFilename` 去扩展名，空文件名回退「未命名文档」。
3. **状态固定草稿**：上传解析永远产出 `Draft(0)`，**不自动发布**——解析质量不可信，必须走人工审核（课程 54）。

## 7. 主动回忆（完整版答案）

### Q1 为什么不用单一 Loader 覆盖所有格式？

**因为「统一」这件事应该发生在出口，不是入口。**

1. **二进制结构没有共同点**：DOCX/PPTX 是 OOXML（ZIP + XML）只是碰巧同源；XLSX 虽然也是 OOXML 但语义是二维网格；PDF 是绘图指令流 + 字体子集；TXT 只有字节。同一个解析器不可能同时擅长 XML 树遍历和 PDF 指令流还原。
2. **库的抽象层级不齐**：`mammoth` 直接给你 HTML（帮你做了样式→语义映射），`exceljs` 给你单元格矩阵，`jszip` 只给你原始 XML（全部提取逻辑要自己写），`pdf-parse` 只给扁平分页文本（连坐标都没有）。**用单一 Loader 意味着统一到最弱的那个能力**。
3. **「单一 Loader」方案的真实代价**：`UnstructuredLoader` 这类方案能覆盖格式，但本地要拖 OCR/版面模型，部署重、启动慢、质量不可控；云端方案（MinerU）质量高，但引入**外部依赖、token、费用、隐私与超时**。这本质是**自研 vs 采购**的权衡，不是技术选择题。
4. **按格式选最优引擎，才能拿到每种格式的上限**：docx 用 mammoth 才保住 Word 标题层级；xlsx 用 exceljs 才能拿到公式结果和富文本；pptx 用 jszip 才能精确控制「一页一节」。
5. **代价是可维护性**：N 个格式 = N 份解析代码 + N 套测试 + N 个升级风险。所以课程 v20 用 MinerU **把这个复杂度外包出去了**——这是同一权衡下的另一种答案。

> 一句话：**入口分化、出口统一**。统一 Loader 是「入口统一」，省的是维护成本，交出去的是每种格式的解析上限。

### Q2 Markdown 统一层带来什么收益？

1. **一次转换，全链路复用**：存储（Mongo `content`）、切分（chunk）、向量化、全文索引、前端渲染，全都消费同一种字符串。不用为 PDF 写一套切分、为 DOCX 写另一套。
2. **结构信息保留得刚好**：`#` 层级让切分器能按标题切（结构感知分块），GFM 表格让表格能按行切；换成纯文本这两条都做不到。
3. **体积与可读性平衡**：比 HTML 少一个数量级（去掉 style/class/span），比 AST 轻得多，同时**人能直接读、能 diff、能肉眼校对**——这是知识库运维里极其重要的一条。
4. **图片天然可外链**：`![](url)` 一个语法同时解决「图片存哪」和「正文怎么引用」，正好接对象存储。
5. **模型友好**：LLM 语料里 Markdown 密度极高，标题/列表/表格的语义模型都认识；相比之下自定义 JSON schema 需要额外 prompt 教它。
6. **可重建**：正文是**派生数据**，原文件留在 RustFS，随时能换引擎重跑——这让「换 MinerU」这种决策变得低风险。

**代价**：复杂版式（多栏、浮动图、公式）会丢；表格合并单元格无法表达；`|` 要转义；伪标题（加粗当标题用）会让层级失真。

### Q3 解析失败和版面丢失如何降级？

分四层，从「库」到「人」：

**① 库级降级（parser 内部）**

| 场景 | 降级动作 |
| --- | --- |
| pptx 自研 ZIP 失败 | → `officeparser` AST → md |
| xlsx exceljs 失败/文件损坏 | → `officeparser` AST → md |
| pdf 图片提取整批失败 | → 只出文本，warn 不抛错 |
| pdf 单张图上传失败 | → 跳过该张，其余继续 |
| 未启用 RustFS | → 解析照做，`fileUrl=null`，PDF 不出图 |

**② 结果级校验（service 层）**

- 空 buffer / 空结果 → `400`，**拒绝入库**。这是最重要的一条：宁可让用户重传，也不要往知识库里灌空文档。
- 记录 `chars` 与 `elapsed`，字符数异常（过短/过长）可作为后续告警阈值。

**③ 版面丢失的补偿（设计层）**

- **保留定位信息**：PDF 按页拼装、PPTX 输出 `## 幻灯片 N`，正文虽丢版面但坐标还在，下游能回溯到第几页。
- **图片归属到页**：图片按页追加而不是全丢文末，至少能知道它属于哪一页。
- **表格兜底**：正文没有 `| ---` 时，把 `getTable()` 的结果追加成「检测到的表格」章节，宁可重复也要留住数据。
- **状态兜底**：解析产物一律 `Draft`，不自动发布；靠审核（课程 54）兜住质量。

**④ 人工与可观测（运维层）**

- 原文件永久留 RustFS → 换引擎/修 bug 后**可重跑**，解析失败不是终态。
- 失败原因写进日志（扩展名、文件名、字符数、耗时、异常消息），这是排查线上问题的唯一线索。
- 已知案例：本文档记录的 pdf 多栏错序，就是靠「教育经历与九江学院相隔 37 行」这种可量化指标发现的。**能测量的缺陷才可能被修复。**

> 反面做法：静默吞掉解析异常并写入空正文。它在测试环境看起来「一切正常」，在生产会变成大量无正文的僵尸文档。

## 8. 面试追问速答

1. **为什么不用一个通用 Loader？**
   入口的二进制结构和库抽象层级差异太大，统一 Loader 会拉平到最弱能力；且通用方案通常要拖 OCR/大模型，部署成本高。正确做法是入口分化、出口统一到 Markdown。
2. **为什么 Markdown 而不是 JSON AST？**
   Markdown 是「够用 + 零成本消费」的折中：下游切分/向量化/渲染/人工校对全都能直接吃；AST 保真度高但每条链路都要写适配。
3. **PDF 为什么最难？**
   PDF 不存结构只存绘制指令，文字顺序是内容流顺序而非阅读顺序；拿不到坐标就无法按视觉位置重排。要么换引擎（MinerU/officeparser），要么接受降级。
4. **大文件怎么处理？**
   当前是同步解析（50MB 上限内阻塞请求）。生产应改成「上传即返回 → 异步解析 → 状态轮询」，否则一个 50MB PDF 会占满 worker（课程 51 的异步流水线）。
5. **图片为什么要放对象存储，不能存 Mongo/本地盘？**
   Mongo 单文档 16MB 且不适合大二进制；本地盘在多实例下读不到、无法备份扩容。对象存储给 URL，正文只存引用。
6. **中文文件名为什么会乱码？**
   multipart 的 `filename` 按 RFC 传的是字节，busboy 用 Latin-1 解码；需要按 Latin-1 取字节再 UTF-8 还原。
7. **解析器为什么要做成纯函数？**
   可单测（喂 buffer 断言 markdown）、可放队列、可换引擎（换 pdf 引擎只改一个函数）。副作用都上移到 service。
8. **换解析引擎的成本有多高？**
   只要守住 `(buffer) => markdown` 契约，换引擎就是换一个文件——课程从 pdf-parse 换到 MinerU 就是这个结构撑住的。

## 9. v2 踩坑记录（真实发生）

| 现象 | 根因 | 结论 |
| --- | --- | --- |
| `TS2694 Namespace 'global.Express' has no exported member 'Multer'` | `tsconfig` 的 `types` 是白名单，`@types/multer` 装了也不会自动加载 | 装包不够，还要把 `"multer"` 加进 `types` 数组（全局声明类包都需要） |
| `ERR_AMBIGUOUS_MODULE_SYNTAX: both require() and top-level await` | 课程代码是 CJS，本项目 `"type": "module"`，`require` 在 ESM 作用域是 `undefined` | 改 `import { gfm } from 'turndown-plugin-gfm'`；CJS 包靠 cjs-module-lexer 提供具名导出 |
| `Cannot find module '...\dist\main'` | 上游 `.ts` 有 TS 报错时 `tsc` **不产出任何文件** | 先修编译错误；`nest build` exit 0 才有 dist |
| `ECONNREFUSED` on `TypeOrmModule` | Postgres 容器没起（15432 不通） | 用端口探测判断，别信 compose 的 healthcheck（库名写错会永远 unhealthy） |
| `turndown-plugin-gfm` 报「找不到声明文件」 | 包内无 `.d.ts`，npm 上也无 `@types/turndown-plugin-gfm`（404） | 自写 `src/types/turndown-plugin-gfm.d.ts`，声明为 `TurndownService.Plugin` |
| PDF 章节顺序错乱（教育经历/九江学院相隔 37 行） | `pdf-parse` 只给 `{num,text}`，无坐标，多栏无法重排 | 引擎能力边界 → 换 officeparser / MinerU |
| xlsx 日期全是 `2019-03-01T00:00:00.000Z` | `cellToString` 对 `Date` 直接 `toISOString()` | 手动格式化为 `YYYY-MM-DD` |
| 图片把句子「切断」 | 图片按页追加在整页文本之后 + 句子本身跨页 | 视觉噪音，非逻辑错误；换成「图片归页尾并标注页码」更易读 |
