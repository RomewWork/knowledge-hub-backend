# 知识图谱链路 v5 总结（发布 → MQ → 分块 → LLM 抽实体 → Neo4j）

> 对应课程：53 企业级知识库项目 · 文档抽取 Neo4j 知识图谱的实体（前情见 `docs/异步RAG流水线v3总结.md`、`docs/全文检索链路v4总结.md`）
> 代码基线：`ai-agent-code/knowledge/knowledge-hub-backend`（学习项目，**v5 改动全在工作区、尚未提交**；仓库最后一次提交是 `de71e99 feat: v4`）
> 技术栈：Nest + amqp-connection-manager/amqplib + **neo4j-driver 6.2** + **zod 4.4** + @langchain/openai（ChatOpenAI） + RabbitMQ 3.13 + Neo4j (latest, APOC) + ES 8.17 / PG16 / MongoDB 7
> 整理时间：2026-10-29

---

## 0. 一页速览

v5 在 v3（RAG 向量）、v4（Search 全文）之后**并出第三条派生索引**：发布时多投一条 KG 事件，消费者读正文 → **复用 RAG 同款分块** → 逐块用 LLM 抽「实体 + 关系」→ 写入 Neo4j。这是「发布 → 三路索引」的最后一块拼图。

关键认知先行：**v5 只做「写图」这一半。** 没有任何图谱查询接口，也没有实体消歧与图谱检索——本讲交付的是**图谱摄取链路**，不是「GraphRAG / 图谱问答」。

| 维度 | 结论 |
| --- | --- |
| 入口 | `PUT /documents/:id/publish`（无审核、无鉴权，见 54/55） |
| 新增触发点 | `afterPublish()` 里 **RAG + Search + KG 三条消息**（`Promise.all`）；未新增 HTTP 接口 |
| 交换机 | 新增 `kg.graph.exchange`（`topic`, durable） |
| 队列 / 路由键 | `kh.kg.graph.queue` / `kg.graph.build.by_ids`（BUILD）、`kg.graph.delete`（DELETE） |
| 消息体 | `{ taskId, type:'BUILD_BY_DOC_IDS', documentIds:[id] }`，**只带 ID，不带正文** |
| 消费入口 | `DocumentPipelineConsumer.handleKg()` → `PipelineOrchestrator.handleKgBuild()` |
| 编排 | 只有分发：`BUILD_BY_DOC_IDS` / `BUILD_ALL` 拉文档后 `buildBatch`；`DELETE_BY_DOC_IDS` 直接删 |
| 图模型 | `(KnowledgeDocument)-[:HAS_CHUNK]->(DocumentChunk)-[:MENTIONS]->(KnowledgeEntity)`；`(Entity)-[:RELATED_TO]->(Entity)` |
| 索引粒度 | 一块（chunk）一次 LLM 调用；实体按 `name` 跨文档复用 |
| 幂等 | 先 `deleteForDocument` 清旧图再建；`MERGE` by `id` / `chunkId` / `name` |
| 降级 | `NEO4J_ENABLED=false` 或启动连不上 → 跳过写图并打 warn，**不阻断发布消费** |
| 新增依赖 | `neo4j-driver@^6.2.0`、`zod@^4.4.3`；docker 新增 `neo4j:latest` |
| 未落地 | 图谱查询接口、实体消歧、version、ack/重试/DLQ、抽取缓存、置信度过滤 |

```
PUT /documents/:id/publish
  │
  ├─ PG: status=Published, publish_time=now()          ← 事实源（同步）
  ├─ Mongo: 读正文 content
  │
  └─ afterPublish(saved, content)
        ├─ triggerRagReindex(id)   ──► rag.reindex.exchange   ──► kh.rag.reindex.queue    └─► 分块 → 嵌入 → kh_chunk
        ├─ triggerSearchIndex(doc) ──► search.index.exchange  ──► kh.search.index.queue   └─► 快照 upsert → kh_document
        └─ triggerKgBuild(id)      ──► kg.graph.exchange      ──► kh.kg.graph.queue
                                                                     └─► 读正文 → 分块 → LLM 抽实体 → Neo4j
                                                                           Document ─HAS_CHUNK→ Chunk ─MENTIONS→ Entity
                                                                                        Entity ─RELATED_TO→ Entity
```

### 0.1 与 v4 的差异（增量清单）

| 类别 | v4 | v5 新增 |
| --- | --- | --- |
| 交换机 | `rag.reindex.exchange` + `search.index.exchange` | `+ kg.graph.exchange`（topic, durable） |
| 队列 | `kh.rag.reindex.queue` + `kh.search.index.queue` | `+ kh.kg.graph.queue` |
| 路由键 | `rag.*` + `search.*` | `+ kg.graph.build.by_ids`、`+ kg.graph.delete` |
| 消息类型 | `ReindexMessage`、`SearchIndexMessage` | `+ KgBuildMessage`（`BUILD_ALL` / `BUILD_BY_DOC_IDS` / `DELETE_BY_DOC_IDS`） |
| 新增文件 | `src/pipeline/search-index.service.ts` | `+ graph-build.service.ts`（建图/删图）、`+ extraction.service.ts`（LLM 抽取）、`+ kg-extraction.schema.ts`（zod + prompt） |
| 生产端 | `afterPublish` 投 2 条 | 投 **3 条**；`afterUnpublish()` 也补了 KG 删除 |
| 消费端 | 注册 RAG + Search | 构造器再注册一个 `KG_GRAPH_QUEUE` handler |
| 编排 | `handleRagReindex` / `handleSearchIndex` | `+ handleKgBuild()` |
| 编排器依赖 | 6 个 | `+ GraphBuildService` |
| 基础设施 | rabbitmq / es / kibana / pg / mongo / rustfs | `+ neo4j`（APOC） |
| 运行依赖 | — | `+ neo4j-driver`、`+ zod` |
| 数据流 | 发布 → 两路索引 | 发布 → **三路并行**，互不阻塞 |

**v5 没有动的**：`rabbitmq.service.ts` 的 ack 逻辑（仍然只 `nack`、不 `ack`）、分块参数、embedding、`kh_chunk` / `kh_document` mapping、`document.service.ts` 的 `remove()/update()`。

### 0.2 一句话结论

**v5 用「只传 ID + 消费时回查正文」把图谱摄取接进发布链路，三级模型（文档/块/实体）让实体可溯源、可按文档清理；但链路只到「写图」为止 —— 没有图谱查询、没有实体消歧、没有 ack/版本号，LLM 成本还随文档量线性增长。**

### 1.1 一个必须知道的坑：拓扑漏声明 → 启动即 404

v5 第一版落地时，`rabbitmq.service.ts#assertTopology()` **只声明了 RAG + Search**，但消费者已经注册了 `KG_GRAPH_QUEUE`。结果：

```
WARN [RabbitMqService] RabbitMQ 断开：Channel closed by server: 404 (NOT-FOUND)
   with message "NOT_FOUND - no queue 'kh.kg.graph.queue' in vhost '/'"
Error: Operation failed: BasicConsume; 404 (NOT-FOUND) ...
```

根因：`bindConsumers()` 去 `consume('kh.kg.graph.queue')` 时，队列从没被 `assertQueue` 过。**MQ 里「消费者注册」和「拓扑声明」是两件事，声明漏一个，消费就 404 崩进程。**

正确做法（当前工作区已修）：

```ts
private async assertTopology(ch: ConfirmChannel) {
  // RAG ...  Search ...

  await ch.assertExchange(KG_GRAPH_EXCHANGE, 'topic', { durable: true });
  await ch.assertQueue(KG_GRAPH_QUEUE, { durable: true });
  await ch.bindQueue(KG_GRAPH_QUEUE, KG_GRAPH_EXCHANGE, KG_RK_BUILD_BY_IDS);
  await ch.bindQueue(KG_GRAPH_QUEUE, KG_GRAPH_EXCHANGE, KG_RK_DELETE);

  this.logger.log('RabbitMQ 拓扑已声明（RAG + Search + KG）');
}
```

> 排障口诀：**看到 `404 ... no queue`，先查 `assertTopology` 是否声明了同名队列，再查 routing key 拼写。**

## 2. MQ 拓扑：第三条链路

### 2.1 拓扑（`src/mq/mq.constans.ts` + `rabbitmq.service.ts#assertTopology`）

| 对象 | 名称 | 参数 | 作用 |
| --- | --- | --- | --- |
| Exchange | `kg.graph.exchange` | `topic`, durable | 接收 KG 建图 / 删图事件 |
| Queue | `kh.kg.graph.queue` | durable | 本服务消费 |
| Binding | `kg.graph.build.by_ids` | — | `BUILD_BY_DOC_IDS` / `BUILD_ALL`：建图 |
| Binding | `kg.graph.delete` | — | `DELETE_BY_DOC_IDS`：删图 |
| Exchange | `rag.reindex.exchange` | `topic`, durable（v3 已有） | RAG |
| Exchange | `search.index.exchange` | `topic`, durable（v4 已有） | Search |

**设计取向**：三条链路**三条独立 exchange/queue**，不共用。理由和 v4 §2.1 一致，但 KG 多两条：

1. **消费形态完全不同**：RAG 消费 embedding API、Search 消费 ES 写入、KG 消费 **LLM 抽取（最慢最贵）**。共用队列会让「慢的 KG」堵住「快的 Search」。
2. **消息形态不同**：RAG/KG 只带 ID（小），Search 带快照（大）。同队列会让大消息拖慢小消息节奏。
3. **可独立扩缩容与限流**：KG 是成本大头，将来要单独限速 / 单独 DLQ，必须独立队列。

### 2.2 命名与文件名（沿用 v4 的坑）

- `mq.constans.ts`（应为 `constants`）、`pipeline.messagets.ts`（应为 `messages`）拼写错误**没修**。
- v5 新增常量全部写进这两个文件，所以**拼写错误被继续沿用**——引用路径时注意别"自作主张"改成正确拼写，否则 import 会断。

## 3. 生产端：只发 documentIds

### 3.1 `afterPublish()` 的三投递

```ts
async afterPublish(document: DocumentEntity, content?: string | null) {
  await Promise.all([
    this.triggerRagReindex(document.id),
    this.triggerSearchIndex(document, content),
    this.triggerKgBuild(document.id),      // ← v5 新增
  ]);
}
```

KG 消息**只带 `documentIds`**，不带正文：

```ts
const message: KgBuildMessage = {
  taskId: randomUUID(),
  type: 'BUILD_BY_DOC_IDS',
  documentIds: [documentId],
};
await this.rabbit.publish(KG_GRAPH_EXCHANGE, KG_RK_BUILD_BY_IDS, message);
```

### 3.2 为什么 KG 不带正文（与 Search 相反）

| 链路 | 消息 | 原因 |
| --- | --- | --- |
| Search | 文档快照（正文截 1000 字） | 全文索引要「发布那一刻」的版本；少一次跨库读 |
| RAG / KG | 只带 ID | 都要读**全文**（分块 / 抽实体），正文几十 KB~MB 塞不进消息；消费时回查能拿最新正文 |

> 这解释了课程里那句关键设计：**「文档快照就是通过消息传递的文档关键字段」只对 Search 成立**。KG 和 RAG 一样按 ID 回查。

### 3.3 `afterUnpublish()` 也补了 KG 删除

v4 时 `afterUnpublish()` **没有调用方**（是个悬空函数）。v5 里它已经补上 KG 删除分支（`triggerKgDelete` → `kg.graph.delete`），但**调用方仍然是 `remove()` 之外**——`document.service.ts` 的 `remove()` 是否真的调了 `afterUnpublish`，需要在 54/55 补删除链路时确认（当前 v5 未改动 `remove()`）。

## 4. 消费端：handleKg → handleKgBuild

```ts
// 构造器里注册（早于 RabbitMqService.onModuleInit 的 bindConsumers）
this.rabbit.registerHandler(KG_GRAPH_QUEUE, (msg) => this.handleKg(msg));

/** KG：分块 → 抽实体关系 → Neo4j */
private async handleKg(msg: ConsumeMessage) {
  const body = this.parseJson<KgBuildMessage>(msg);
  this.logger.log(`[KG] type=${body.type}, ...`);
  await this.orchestrator.handleKgBuild(body.type, body.documentIds);
}
```

编排器只有分发，不做业务：

```ts
async handleKgBuild(type: string, documentIds?: string[]) {
  if (type === 'DELETE_BY_DOC_IDS' && documentIds?.length) {
    for (const id of documentIds) await this.graphBuildService.deleteForDocument(id);
    return;
  }
  const docs =
    type === 'BUILD_BY_DOC_IDS' && documentIds?.length
      ? await this.loadDocumentsByIds(documentIds)
      : type === 'BUILD_ALL'
        ? await this.loadAllPublishedDocuments()
        : [];
  if (!docs.length) { this.logger.warn(...); return; }
  await this.graphBuildService.buildBatch(docs);
}
```

要点：

- `BUILD_ALL` 是**全量重建**入口（拉所有已发布未删除文档），没有分页/限流——文档多了会一次性打爆 LLM 配额。
- `loadDocumentsByIds` 回查 **Postgres 元数据 + Mongo 正文**，拼成 `PipelineDocument`，和 RAG 完全同源。

## 5. 建图层：GraphBuildService（核心）

### 5.1 图模型

```
(KnowledgeDocument {id, title, summary, categoryId, authorId, status})
   └─[:HAS_CHUNK {chunkIndex}]→ (DocumentChunk {chunkId, documentId, content, heading, chunkIndex, totalChunks})
        └─[:MENTIONS]→ (KnowledgeEntity {name, type, description, aliases})
                          └─[:RELATED_TO {relation, weight}]→ (KnowledgeEntity)
```

### 5.2 单篇构建 `buildForDocument()` 五步

| 步 | 动作 | 幂等键 |
| --- | --- | --- |
| 0 | `deleteForDocument(doc.id)` **先清旧图** | doc id |
| 1 | `MERGE (d:KnowledgeDocument {id})` + SET 元数据 | `id` |
| 2 | 复用 `ChunkingService.chunk()` 分块（与 RAG 同参数） | — |
| 3 | 每块 `MERGE (c:DocumentChunk {chunkId})` + `MERGE (d)-[:HAS_CHUNK]->(c)` | `chunkId` |
| 4 | 每块 `extractionService.extract()` → `writeExtraction()` | — |

两个重要的「跳过」：

```ts
if (!this.driver)  { /* Neo4j 不可用 */ return 0; }
if (!doc.content?.trim()) { /* 空正文 */ return 0; }
```

以及**单块抽取失败不阻断整篇**：

```ts
try {
  extracted = await this.extractionService.extract(chunk.content, chunk.heading, doc.title);
} catch (e) {
  this.logger.error(`KG 抽取失败，跳过该块：...`);
  extracted = { entities: [], relations: [] };
}
```

### 5.3 写图 `writeExtraction()`：实体 / MENTIONS / RELATED_TO

**实体按 name 合并，跨文档复用**：

```cypher
MERGE (e:KnowledgeEntity {name: $name})
ON CREATE SET e.type = $type, e.description = $description,
              e.aliases = $aliases, e.createdAt = $now, e.updatedAt = $now
ON MATCH  SET e.type = coalesce($type, e.type),
              e.description = CASE WHEN $description <> '' THEN $description ELSE e.description END,
              e.updatedAt = $now
```

**块 → 实体**（注意 `MATCH` 不是 `MERGE`）：

```cypher
MATCH (c:DocumentChunk {chunkId: $chunkId})
MATCH (e:KnowledgeEntity {name: $name})
MERGE (c)-[:MENTIONS]->(e)
```

**实体 → 实体**（边类型统一 `RELATED_TO`，具体语义放边属性 `relation`）：

```cypher
MATCH (a:KnowledgeEntity {name: $source})
MATCH (b:KnowledgeEntity {name: $target})
MERGE (a)-[r:RELATED_TO]->(b)
ON CREATE SET r.relation = $relType, r.weight = $weight, r.createdAt = datetime()
ON MATCH  SET r.weight = coalesce($weight, r.weight)
```

> 设计取舍：**只用一个边类型 `RELATED_TO`，把 12 种语义塞进 `relation` 属性**。好处是图 schema 简单、加新关系不用改边类型；代价是「查所有 CAUSES 关系」要 `WHERE r.relation='CAUSES'`，走不了边类型索引。

### 5.4 分块参数（复用 RAG，保证粒度一致）

`ChunkingService`：`RAG_CHUNK_SIZE=512` token、`RAG_CHUNK_OVERLAP=64` token，`CHARS_PER_TOKEN=2` → 约 **1024 字符/块、128 字符重叠**；`chunkId = sha256(documentId:chunkIndex).slice(0,64)`。

**同一篇文档，RAG 的块和图谱的块是同一套 `chunkId`** —— 这是 v5 的一个重要设计：图谱实体能反查到向量块，反之亦然。

## 6. 抽取层：ExtractionService + schema（核心）

### 6.1 调用方式

```ts
const llm = new ChatOpenAI({
  apiKey, model,                 // 默认 qwen-plus
  temperature: 0.1,              // 低温：抽取要稳定
  timeout: timeoutMs,            // KG_LLM_TIMEOUT_MS，默认 60000
  maxRetries: 0,                 // 不自动重试，失败交给上层跳过
  useResponsesApi: false,        // DashScope 走 Chat Completions
  configuration: { baseURL: baseUrl },
});
this.structuredLlm = llm.withStructuredOutput(kgExtractionResultSchema, {
  name: 'extract_knowledge_graph',
});
```

输入：`system`（抽取规则+类型清单）+ `user`（文档标题 / 章节 / **正文截 4000 字**）。

### 6.2 zod schema 的两个「反直觉」设计

```ts
type: z.string().describe('实体类型').optional(),      // ← 不是 enum
relation: z.string().describe('关系类型').optional(),  // ← 不是 enum
```

注释写得很清楚：**模型常返回中文类型或自造类型（如 `APPLIES_TO`），用 enum 会让整块校验失败、整段抽取丢失。** 所以故意放宽为 `string`，再由 `normalizeEntityType` / `normalizeRelationType` 归类：

```ts
normalizeEntityType(raw)   // 命中 10 类枚举 → 原值；否则 → 'CONCEPT'
normalizeRelationType(raw) // 命中 12 类枚举 → 原值；否则 → 'RELATED_TO'
```

### 6.3 后处理 `toExtractionResult()`：三道清洗

1. **数量截断**：`slice(0, maxEntities=12)` / `slice(0, maxRelations=15)`，防图爆炸。
2. **类型归一**：上面的 `normalize*`。
3. **丢挂空关系**：`source`/`target` 不在本块实体集里的关系直接 `continue`——**避免悬空边**（这也是 `writeExtraction` 用 `MATCH` 的配套）。

另外：`name` 为空跳过、`aliases` 去空白、`weight` 缺省补 `0.5`。

### 6.4 实体 10 类 / 关系 12 类

| 实体（`KG_ENTITY_TYPES`） | 关系（`KG_RELATION_TYPES`） |
| --- | --- |
| PERSON 人/角色 | HAS_PART 组成、包含 |
| ORGANIZATION 组织/部门 | BELONGS_TO 归属 |
| CONCEPT 术语/概念 | RELATED_TO 泛关联（兜底） |
| DOCUMENT 文档/规范 | DEFINES 定义 |
| PROCESS 流程/活动 | REQUIRES 前置、依赖 |
| PRODUCT 产品/系统 | USES 使用 |
| LOCATION 地点 | RESPONSIBLE_FOR 负责 |
| TIME 时间/周期 | PARTICIPATES_IN 参与 |
| POLICY 政策/制度 | LOCATED_IN 位于 |
| RESOURCE 工具/设备 | OCCURS_AT 发生于 |
| | CAUSES 导致 |
| | CONFLICTS_WITH 冲突/例外 |

> 课程原话：**三级结构（文档/chunk/实体）是确定的，具体实体和关系要按业务领域固定。** 工业、医疗、企业行政各有各的类型表。

## 7. 删除链路与孤儿实体清理

`deleteForDocument()` 两条 Cypher：

```cypher
// ① 删文档 + 它的所有块（DETACH 一并拆掉相连的 HAS_CHUNK / MENTIONS 边）
MATCH (d:KnowledgeDocument {id: $id})
OPTIONAL MATCH (d)-[:HAS_CHUNK]->(c:DocumentChunk)
DETACH DELETE c, d

// ② 清孤儿实体：没有任何 chunk MENTIONS 的实体视为无引用，整节点删除
MATCH (e:KnowledgeEntity)
WHERE NOT (e)<-[:MENTIONS]-()
DETACH DELETE e
```

为什么要两步：

- 只删文档不删块 → 块成孤儿，图膨胀。
- 删了块不清实体 → 实体失去所有来源，既无法溯源、也永远删不掉，图只增不减。
- **孤儿清理是「按文档删」能做到精确的前提**：删一篇文档，只删它独有的实体；被别的文档还在引用的实体保留。

> 这也是「三级模型为何比只存实体可靠」的运维版答案：**没有 MENTIONS 边，你就没法回答「这个实体还有没有来源」。**

## 8. 幂等与降级

### 8.1 幂等矩阵（v5 真实行为）

| 操作 | 幂等键 | 重复执行结果 |
| --- | --- | --- |
| 建图（同文档重发） | 先 `deleteForDocument` + `MERGE` | 节点/边**不翻倍**，全量替换 ✅ |
| 文档节点 | `id` | 覆盖元数据，`createdAt` 保留首次 ✅ |
| 块节点 | `chunkId = sha256(docId:index)` | 覆盖 ✅ |
| 实体 | `name` | 跨文档复用，多个 chunk 都指过来 ✅ |
| 关系 | `MERGE (a)-[RELATED_TO]->(b)` | `ON MATCH` 只更新 weight ✅ |
| 删图 | `DETACH DELETE` + 孤儿清理 | 重复删无副作用 ✅ |

**但缺「顺序保护」**：没有 `version` 字段，先发的 DELETE、后到的 BUILD（乱序/重投）会让**文档在图里复活**。幂等只保证「同一操作重复结果相同」，不保证「不同操作按正确顺序生效」。

### 8.2 降级：Neo4j 不可用不阻断发布

```ts
async onModuleInit() {
  if (!this.enabled) { warn; return; }
  this.driver = neo4j.driver(uri, neo4j.auth.basic(user, password));
  try { await this.driver.verifyConnectivity(); }
  catch { warn; await this.driver.close(); this.driver = null; }   // ← 永久降级
}
```

- 启动连不上 → `driver=null`，`buildForDocument` / `deleteForDocument` 直接 return，日志 warn。
- **进程内不会自动重连恢复**（和 v4 的 ES 降级同一个问题）。
- 与 RAG/Search 一致的哲学：**派生副本失败，不能拖垮「发布」这个事实源操作。**

### 8.3 一个密码陷阱

`docker-compose.yml` 里 Neo4j 是 `NEO4J_AUTH=neo4j/12345678`，而代码默认值是：

```ts
const password = this.config.get('NEO4J_PASSWORD', 'password');   // ← 默认 'password'
```

**不配 `NEO4J_PASSWORD=12345678`，连不上，直接进降级分支（静默跳过建图）。** 这是 v5 最容易"以为跑通了其实没写图"的坑——查日志有没有 `Neo4j 已连接`。

## 9. 缺口清单与 v6 待办

**P0（正确性/数据）**

1. `buildForDocument` 先删后建：删成功、建失败 → **该文档图谱短暂为空**（且无补偿）。
2. 无 `version`：乱序/重投时旧 BUILD 覆盖新图、DELETE 后复活。
3. `afterUnpublish()` 的调用方未确认：`remove()` 若不发事件，删文档后图谱残留。
4. 实体**只按 `name` 合并，没有消歧**：同名不同义（如两个部门都叫"研发中心"）被错误合并；`aliases` 存了但没参与匹配。
5. LLM 抽取**无置信度过滤**：`weight` 存了却不用，低置信实体照样入图。

**P1（成本/可运维）**

6. **每个 chunk 一次 LLM 调用**：成本随文档量线性增长，无缓存、无批处理、无并发上限。
7. `BUILD_ALL` 全量重建无分页/限流，容易打爆配额与 Neo4j 写入。
8. 消费成功不 `ack`（v3/v4 遗留）：unacked 堆积 + 重启全量重投（建图幂等所以无害，但浪费 LLM 成本）。
9. 无 DLQ/重试：KG 消息失败 `nack(requeue=false)` 直接丢。
10. Neo4j 启动不可用 → 永久降级不恢复。

**P2（工程卫生）**

11. 无图谱查询接口：**只写不查**，本讲交付的是「摄取」不是「检索」。
12. `mq.constans.ts` / `pipeline.messagets.ts` 拼写错误延续。
13. 单边类型 `RELATED_TO` + `relation` 属性 → 按关系类型查询要过滤属性，走不了边类型索引。

**v6 建议顺序**：① 图谱查询接口 + 消歧（让图可用、可信）→ ② version + ack/DLQ（让顺序与失败可控）→ ③ 抽取缓存 + 并发上限（控成本）→ ④ 置信度阈值 + 实体合并策略。

## 11. 主动回忆（完整版答案）

### Q1 三级模型为何比只存实体更可靠？

**因为「只存实体」回答不了三个问题：实体从哪来、删文档时删谁、抽错了怎么查。**

1. **可溯源**：`(c:DocumentChunk)-[:MENTIONS]->(e:KnowledgeEntity)` 把实体锚定到具体 chunk，chunk 带 `content/heading/chunkIndex`，能回到原文哪一段。只存实体则完全不知道出处。
2. **可清理**：删文档 = 删 `Document` + 其 `HAS_CHUNK` 的 chunk，再清「入边 MENTIONS 为空」的孤儿实体。只存实体时，**你无法判断某实体是否还被别的文档引用**——要么不敢删（图只增不减），要么误删。
3. **可复用不丢来源**：实体按 `name` MERGE 跨文档复用，靠多个 chunk 的 MENTIONS 保留全部来源；只存实体只有一个节点，来源信息已经丢了。
4. **可解释/可审计**：回答「这个结论来自哪篇文档哪一段」依赖 MENTIONS + chunk 正文；实体抽错时能定位到对应 chunk 重抽。

> 一句话：**三级 = 可溯源 + 可清理 + 可解释；实体名只是图的节点标签，MENTIONS 才是图的骨架。**

### Q2 实体类型与关系为什么要按领域定制？

**因为「抽什么」决定图谱的价值密度，而它是领域相关的；但「怎么组织」是通用的。**

1. **通用抽取必然产生噪音**：不加约束时 LLM 会抽出「系统」「数据」「功能」「问题」这类泛化词，图谱大而空，查询价值极低。prompt 里第 2 条规则就是明令禁止。
2. **收敛枚举才能校验与复用**：实体 10 类、关系 12 类是一组有限词汇表，`normalize*` 把模型输出归到枚举，下游查询、可视化、权限过滤才有稳定 schema。
3. **领域决定词汇表**：医疗要抽「症状/药品/检查」，工业要抽「设备/工序/工单」，企业行政抽「部门/制度/流程」。同一套三级结构，换一张类型表即可。
4. **结构不变、语义可变**：`Document → Chunk → Entity` 这三级是**确定的、与领域无关**（课程原话），变的是实体与关系的具体类型。

> 一句话：**三级结构是骨架（通用），实体关系是血肉（领域定制）；定制的是词汇表，不是模型。**

### Q3 怎样处理重复实体和错误抽取？

**重复靠 `MERGE` 业务键，错误靠「放宽 schema + 归一 + 丢弃 + 跳过」四层兜底。**

1. **重复实体**
   - `MERGE (e:KnowledgeEntity {name: $name})` 按实体名幂等，同一实体跨文档/跨 chunk 自动复用，不会重复建节点。
   - `ON CREATE` 写首次 `createdAt`；`ON MATCH` 只更新 `type/description/aliases/updatedAt`，不覆盖首次信息。
   - 边同样 `MERGE`，`ON MATCH` 只刷新 `weight`。
2. **错误抽取**
   - **放宽 schema**：`type`/`relation` 用 `string` 而非 enum，避免一个脏值让整块校验失败。
   - **归一**：`normalizeEntityType` → 未知归 `CONCEPT`；`normalizeRelationType` → 未知归 `RELATED_TO`。
   - **丢弃悬空边**：`toExtractionResult` 里 source/target 不在本块实体集就 `continue`；`writeExtraction` 用 `MATCH` 找两端，实体不存在自然不建边。
   - **失败隔离**：单块 `extract()` 抛错 → catch 后 `{entities:[],relations:[]}`，不阻断其余块；整篇失败由 `buildBatch` 逐篇 catch。
3. **数量爆炸**：`maxEntities=12` / `maxRelations=15` 截断 + prompt 明令不抽泛化词。
4. **残留清理**：删文档后清「无 chunk 指向」的孤儿实体，并 `DETACH DELETE` 掉其 `RELATED_TO` 残边。
5. **已知不足**：同名不同义会被错误合并（无消歧）；`aliases` 存了但没参与匹配；`weight` 没做阈值过滤。

> 一句话：**幂等解决「重复」，归一+丢弃+跳过解决「错误」；但「同名不同义」这个真正的消歧问题，v5 还没解决。**

## 12. 面试追问速答

1. **为什么 KG 不像 Search 那样带快照？**
   抽实体要读**全文**（每块都要送 LLM），正文塞不进消息；消费时回查 PG+Mongo 还能拿最新正文。代价是消费侧多一次跨库读、且并发时可能读到"比消息更新"的正文（同样需要 version）。
2. **为什么三条链路要三个 exchange/queue？**
   消费形态差异巨大（embedding API / ES 写入 / LLM 抽取），故障域和耗时完全不同；KG 最慢最贵，必须能独立限流、扩缩容、配 DLQ。
3. **为什么先删后建，而不是直接 upsert？**
   内容变短时只 upsert 会留下**尾部旧块/旧边**；全量替换才能保证「图 = 当前文档」。代价是删成功、建失败会短暂空图。
4. **为什么实体只用一个 `RELATED_TO` 边类型？**
   schema 简单、加新关系不用改边类型；代价是语义查询要过滤 `r.relation` 属性，用不上边类型索引。
5. **为什么 schema 故意不用 enum？**
   模型常返回中文或自造类型，enum 一旦不匹配会**整块校验失败丢整段抽取**；放宽为 string + normalize 兜底，容错性高得多。
6. **LLM 抽取的成本怎么控？**
   `maxEntities/maxRelations` 截断、正文截 4000 字、temperature 0.1 稳定输出、单块失败跳过。**但成本仍是每块一次调用、随文档线性增长**——这是 KG 与 RAG/Search 最大的工程差异，也是 v6 要加缓存/批处理的原因。
7. **实体消歧怎么做？**
   v5 只按 `name` MERGE。正解：`aliases` 参与匹配、加实体类型约束（同名不同类型不合并）、相似度聚类、人工审核队列、或引入 embedding 做实体链接。
8. **Neo4j 挂了会怎样？**
   启动时连不上 → `driver=null` 永久降级，建图/删图静默跳过，**发布仍成功**。进程内不自动恢复，需重启。
9. **怎么验证图谱是对的？**
   `Neo4j 已连接` 必须有；一篇文档 = 1 Document + N Chunk；每块一条 HAS_CHUNK；重复发布节点数不变；删文档后独有实体消失、共享实体保留、无孤儿实体。
