# 文档检索可见性控制 v15 总结

> 课程 63 · 后端 `knowledge-hub-backend`（v15）· 前端 `knowledge-hub-frontend`（v15）
> 整理时间：2026-11-13

## 一句话

**从「功能权限」进入「数据权限」**：把"谁能看哪篇文档"建模成 `isPublic / teamId / authorId / status`，在**四个查询入口**（文档 SQL、ES 文档、ES 块、Neo4j）各做一次同构过滤，并补一条"改可见性只刷字段、不重算内容"的同步通路。

## 与 v14 的差异

| 维度 | v14 | v15 |
|---|---|---|
| 权限层 | 功能权限（`@RequirePermission`） | **+ 数据权限（行级）** |
| 检索 | 所有人看到同一批结果 | 按 `scope` 过滤 |
| 图谱 | 全量节点 | 按文档可见性过滤 |
| 身份 | `roles` / `permissions` | **+ `teamIds`** |
| 可见性变更 | 无（改了也不生效） | `updateVisibility` 同步三套索引 |

## 访问规则（三条，命中任一即可见）

```
① 管理员 / 审核员          → unrestricted，全部可见
② 作者本人                  → 可见（不论公开/团队/状态）
③ 已发布 且 (isPublic OR teamId ∈ 我的团队) → 可见
```

推论：**草稿 / 待审核 / 已归档，只有作者和管理员能看到。**

## 核心：`document-access.ts`

单一事实源，把同一条规则翻译成三种"方言"：

| 适配器 | 用于 | 关键点 |
|---|---|---|
| `canReadDocument` / `canWriteDocument` | 内存判断（详情、审核） | 先判作者，再判状态 |
| `esVisibilityFilter(scope, fields)` | ES | `bool.should + minimum_should_match:1`；unrestricted 返回 **`null`**（不是空对象） |
| `neo4jDocumentAccessWhere(alias)` | Cypher | `($unrestricted OR authorId=... OR isPublic=true OR teamId IN ...)` |

**两份字段映射**（很容易写错）：

```
kh_document → isPublic / authorId / teamId      (camelCase)
kh_chunk    → is_public / author_id / team_id    (snake_case)
```

## `teamIds` 从哪来

```
① kh_team_member.user_id
② ∪ kh_team.leader_id = userId      ← 负责人可能不在成员表
③ 去重（bigint 统一 String）
④ 过滤 kh_team.deleted = false
```

在 `user.service.toAuthUser()` 里注入，**每次请求回查**（换团队立即生效）。

## 四处落地

| 入口 | 位置 | 写法 |
|---|---|---|
| 文档列表 | `document.service.findAll` | SQL：`author_id = me OR (status=1 AND (is_public OR team_id IN ...))` |
| 文档详情 | `document.service.findOne` | `canReadDocument` 校验，越权抛 403/404 |
| 全文检索 | `search-index` | `wrapEsQuery(multi_match, esVisibilityFilter(...))` |
| RAG 召回 | `vector-index` 的 `keywordSearch` / `knnSearch` | keyword 放 `filter`，knn 放 `knn.filter` |
| 图谱 | `graph-build` 的 `listNodes/listEdges/searchGraph` | Cypher 条件 |
| 审核提交 | `document-review.service` | `canWriteDocument` |

**关键原则**：相关性查询放 `must`，可见性放 `filter`——否则权限条件会参与打分、把有权看的结果排名压低。

## 可见性变更的同步（本讲最容易漏）

改了 `isPublic/teamId` 后，索引里还是旧值。v15 的解法：

```
document.service.update()
  └─ visibilityChanged && isPublished
       └─ pipeline.updateVisibility(doc)
            ├─ searchIndex.updateVisibility   → es.update（单文档）
            ├─ vectorIndex.updateVisibility   → updateByQuery（该文档全部块）
            └─ graphBuild.updateVisibility    → MATCH 文档节点 SET 属性
```

**为什么不重建**：正文和向量都没变，重建要重跑 embedding + LLM 抽实体（几十秒/篇）。只改三个字段就够了。

## 本次实战踩的两个坑（很有价值）

### 坑 1：`term` 写成少数形式

```
[bool] failed to parse field [should]
[term] query does not support array of values
```

`term` 只接受单值，团队条件是数组必须用 `terms`。

**为什么只在有团队的用户身上炸**：没团队时不进 `if (scope.teamIds.length)` 分支；管理员直接 `return null`。所以 admin 测试一切正常，普通用户一搜就 500。

### 坑 2：可见性变更没有同步

现象：DB 里 `is_public=false, team_id=X`，ES 里 `isPublic=true`、无 `teamId`。
结果：非团队成员能搜到该文档，前端还显示「公开」标签（标签读的是 ES 值）。

根因：`document.service.update()` 只同步"内容变更"，**没有注入 `PipelineOrchestrator`、也没调用 `updateVisibility`**；而 `orchestrator.updateVisibility` 早就写好了，只是没人调用。

修复：注入 orchestrator + 计算 `visibilityChanged` + `syncPipelineAfterUpdate` 增加分支。

### 坑 3（遗留）：存量索引没有新字段

v15 之前的文档，`kh_chunk` 里 `is_public/team_id/author_id` 全是 `null` → 非管理员搜不到任何旧文档。
`ensureVisibilityMapping` 只补 mapping，**不回填数据**。必须重新发布或跑 backfill。

## 易错点

| 坑 | 说明 |
|---|---|
| `term` vs `terms` | 数组必须 `terms`，否则 ES 解析报错 |
| 把权限塞进 `must` | 污染相关性打分 |
| 字段名混用 | doc 是 camelCase，chunk 是 snake_case |
| 默认放行 | 未传 user 时应"拒绝"而不是"不过滤" |
| 只过滤一路召回 | keyword 加了、knn 漏了 = 向量那路全泄露 |
| 详情接口漏鉴权 | 猜 id 就能看 |
| `unrestricted` 返回 `{}` | 语义变了（空 bool 可能匹配全部），必须返回 `null` |
| 索引与库不一致 | 索引只是快照，改了库必须同步 |
| 团队关系变更 | 本讲靠"请求时带 teamIds"解决，不依赖索引里的 team_id 更新 |
| 前端隐藏 ≠ 安全 | 后端过滤才是边界 |

## 验收

```bash
# 普通用户（非作者、非团队成员）搜私有文档
curl -s -X POST localhost:3000/search -H "Authorization: Bearer $USER_TOKEN" \
  -H 'Content-Type: application/json' -d '{"keyword":"发票"}' | jq '.total'   # 期望 0

# 管理员搜同一个词
curl -s -X POST localhost:3000/search -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' -d '{"keyword":"发票"}' | jq '.total'   # 期望 >0

# 改可见性 → 不重新发布，立刻生效
curl -X PATCH localhost:3000/documents/$ID -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' -d '{"isPublic":true}'
```

| 检查点 | 期望 |
|---|---|
| 普通用户搜私有文档 | 0 条 |
| 作者搜自己的草稿 | 能搜到（若已入索引） |
| 团队成员搜团队文档 | 能搜到 |
| 详情接口猜 id | 403 |
| RAG 问答 | 上下文不含无权文档 |
| 图谱页 | 只看得到有权文档的实体 |
| 改可见性 | 立刻生效，无需重新发布 |
| 老文档 | 需重新发布/backfill 才有可见性字段 |

## 主动回忆

1. **为什么要做两次过滤（DB + ES）？**
   列表走 SQL、检索走 ES，存储不同。只在一处做，另一处就是泄漏面：列表挡住了，问答还能召回。

2. **为什么放 `filter` 不放 `must`？**
   `filter` 不参与打分、可缓存；放 `must` 会让权限条件影响 `_score`，出现"有权看的结果排名反而低"。

3. **`minimum_should_match: 1` 的作用？**
   在 `filter` 上下文里，`should` 的语义是"或"，必须至少命中一条（公开 / 作者 / 团队）才可见。

4. **`num_candidates` 为什么是 `k*10`？**
   filter 会削掉候选，预取不足会让 kNN 凑不够 k 条。

5. **待审核文档团队成员能看到吗？**
   不能。规则里"已发布"是前置条件；非作者只能看 `status=1` 的。
