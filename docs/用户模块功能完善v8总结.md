# 用户模块功能完善 v8 总结

> 课程 56 · 代码基线 `ai-agent-code/knowledge/knowledge-hub-backend`（v8）
> 整理时间：2026-11-02

## 一句话

**把「能登录」变成「账号可信、可管理」**：引入 Redis 承载一次性凭证（激活 token / 重置验证码）、引入邮件发送、补全用户与角色的 CRUD，并用 DTO / VO 做入参校验与出参裁剪。

## 新增基础设施

| 项 | 内容 |
|---|---|
| 依赖 | `@nestjs-modules/mailer`、`nodemailer`、`ioredis`（+ `@types/nodemailer`） |
| 容器 | `redis:7-alpine`（6379，带 healthcheck）、`redisinsight`（5540） |
| 模块 | `RedisModule`（全局导出 `RedisService`）、`MailerModule.forRootAsync`（transport 从 ConfigService 读） |
| 环境变量 | `REQUIRE_EMAIL_VERIFICATION`、`APP_PUBLIC_URL`、`MAIL_*`、`REDIS_*` |
| 建表 | `kh_user` 新增 `email_verified SMALLINT DEFAULT 1` |

## 两条主流程

### A. 注册 → 邮箱激活

```
POST /auth/register
  └─ requireEmailVerification = REQUIRE_EMAIL_VERIFICATION === 'true'
      ├─ false → status=1, email_verified=1 → 立即可登录
      └─ true  → status=0, email_verified=0
                  → EmailActivationService.createToken(userId)  → Redis(24h，双 key)
                  → EmailService.sendActivationEmail(链接 = APP_PUBLIC_URL + /auth/verify-email?token=)
                  ↑ 发信失败：删 token + 抛 400（不留半成品）

GET /auth/verify-email?token=xxx
  → consumeToken(token)：读出 userId 并立刻删两个 key（一次性）
  → activateEmail(userId)：email_verified=1、status=1（已激活则幂等返回）
```

### B. 忘记密码

```
POST /auth/password/reset/send-code { email }
  → 查用户（不存在 → 404「该邮箱未注册」）
  → 冷却检查：剩余 TTL > 540s 说明 60s 内发过 → 400
  → 生成 6 位码 → Redis 存 600s → 发邮件
  ↑ 发信失败：删码 + 抛 400

POST /auth/password/reset { email, code, newPassword }
  → verify(code) → hash(newPassword, 10) → 更新 → 删码
```

## 用户 / 角色接口

| 方法 | 路径 | 权限 |
|---|---|---|
| PUT | `/users/me` | 登录 |
| GET | `/users/me/stats` | 登录 |
| PUT | `/users/password/change` | 登录（需旧密码） |
| GET | `/users/page` | 登录 |
| GET/POST/PUT/DELETE | `/users/:id`、`/users` | ADMIN |
| PUT | `/users/:id/password/reset` | ADMIN |
| GET/PUT | `/users/:id/roles` | ADMIN |
| GET/POST/PUT/DELETE | `/roles`、`/roles/:id` | ADMIN（类级 `@Roles`） |
| POST | `/auth/logout` | 登录 |
| GET | `/auth/verify-email` | 公开 |
| POST | `/auth/password/reset/send-code`、`/auth/password/reset` | 公开 |

## Redis key 设计

| 用途 | key | 值 | TTL |
|---|---|---|---|
| 激活（正向） | `email:activation:token:{token}` | userId | 24h |
| 激活（反向） | `email:activation:user:{userId}` | token | 24h |
| 重置验证码 | `password:reset:code:{email小写}` | 6 位码 | 600s |

**为什么激活要两条 key**：点链接只能用 token 找人（正向）；重发邮件时只能用 userId 找到旧 token 作废（反向）。缺一条就会出现「旧链接仍然有效」或「重发无法清理」。

## 关键设计

1. **一次性凭证用 Redis，不用数据库**：天然 TTL、校验即删、无需清理任务；它是「临时状态」不是业务数据。
2. **激活 token 是一次性 + 可作废**：`consumeToken` 读到即删，重发作废旧 token，防重放。
3. **发信失败要回滚凭证**：注册失败删 token、重置失败删码，避免「凭证在、邮件没发」的死数据。
4. **DTO / VO 分离**：DTO 管入参校验（`MinLength(6)`、`IsEmail`），VO 管出参裁剪（`UserVO` 不含 `password`）。
5. **登录四道闸门短路**：用户不存在 → 已禁用 → 未激活 → bcrypt 比对。**昂贵的哈希放最后**，前面任一失败都不做哈希运算。
6. **改密必须验旧密码**：`changePassword` 校验 `oldPassword`，防「拿到 token 就能改密码」。

## 易错点

| 坑 | 说明 |
|---|---|
| `email_verified` 默认值 1 与注册写 0 | 默认 1 是为了兼容存量/种子账号；注册时才显式写 0 |
| `sendResetCode` 抛「该邮箱未注册」 | **会造成邮箱枚举**（与登录统一文案的策略不一致）；建议统一返回成功 |
| 激活先删 token 再更新状态 | `consumeToken` 已删，若随后 `activateEmail` 失败，用户失去可重试链接 |
| 路由顺序 | `/users/me`、`/users/me/stats`、`/users/password/change` 必须在 `/users/:id` 之前 |
| `MAIL_SECURE` 与端口 | 587 配 `false`（STARTTLS）；465 才配 `true`；QQ 邮箱用授权码 |
| `APP_PUBLIC_URL` | 会拼进邮件链接，部署必须改，否则邮件里是 localhost |
| 老库新增列 | `email_verified` 需 migration，`init.sql` 在非空库不执行 |

## 验收

```bash
# 管理员建用户（免审模式）
curl -X POST localhost:3000/users -H "Authorization: Bearer $ADMIN" \
  -H 'Content-Type: application/json' \
  -d '{"username":"tom","password":"123456","email":"tom@x.com"}'

# 个人中心 / 统计
curl localhost:3000/users/me -H "Authorization: Bearer $TOKEN"
curl localhost:3000/users/me/stats -H "Authorization: Bearer $TOKEN"

# 改密（验旧密码）
curl -X PUT localhost:3000/users/password/change -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"oldPassword":"123456","newPassword":"654321"}'

# 角色分配
curl -X PUT localhost:3000/users/$UID/roles -H "Authorization: Bearer $ADMIN" \
  -H 'Content-Type: application/json' -d '{"roleCodes":["ROLE_REVIEWER"]}'

# 删除仍有人用的角色 → 400
curl -X DELETE localhost:3000/roles/$RID -H "Authorization: Bearer $ADMIN"

# 普通用户删用户 → 403
curl -i -X DELETE localhost:3000/users/$UID -H "Authorization: Bearer $USER"
```

| 检查点 | 期望 |
|---|---|
| 免审模式注册 | 立即返回「注册成功，请登录」 |
| 开启验证注册 | 返回「请查收邮件激活」，`status=0` |
| 重复点激活链接 | 第二次提示「激活链接无效或已过期」 |
| 60s 内重复发码 | 400「验证码已发送，请稍后再试」 |
| 验证码用一次后再用 | 失败（已删除） |
| 普通用户调 `/users/:id` | 403 |
| 删除有用户绑定的角色 | 400 |
| `/users/me` 返回 | 不含 `password` |

## 主动回忆

1. **为什么激活 token 用 Redis 而不是 JWT？**
   JWT 无状态、签发即有效，撤销要么等过期要么再维护黑名单；激活 token 需要「一次性 + 可作废 + 自动过期」，Redis 三样天然满足。

2. **两条 key 的反向索引解决什么？**
   正向 `token→userId` 用于点链接激活；反向 `userId→token` 用于重发时定位并作废旧 token。只有正向会导致旧链接永久有效。

3. **登录四道闸门为什么这个顺序？**
   用户不存在/禁用/未激活都是廉价判断，bcrypt 是昂贵运算；先短路再哈希，避免被恶意请求拖慢 CPU。

4. **DTO 和 VO 各防什么？**
   DTO 防止脏数据进入业务（格式、长度、必填）；VO 防止敏感字段流出接口（`password`、`deleted`）。
