# 产品体验完善 v21 总结

> 课程 69 · 后端 `knowledge-hub-backend`（v21）· 前端 `knowledge-hub-frontend`（v21）
> 整理时间：2026-11-18

## 一句话

把"能存能查"变成"能组织、能互动、能外发、能回溯、能触达"：**分类树**做组织，**点赞/收藏/评论**做互动，**带密码与有效期的分享链接**做外发，**版本快照**做回溯，**站内通知**做触达。

## 五项能力与表

| 能力 | 表 | 关键字段 |
|---|---|---|
| 分类 | `kh_category` | `parent_id`（0 为根）、`sort`、`deleted` |
| 评论 | `kh_comment` | `parent_id`（楼中楼）、冗余 `user_name` |
| 点赞 | `kh_document_like` | `UNIQUE(document_id, user_id)` |
| 收藏 | `kh_document_favorite` | `UNIQUE(document_id, user_id)` |
| 分享 | `kh_document_share` | `token UNIQUE`、`expire_at`、`revoked`、`password_hash` |
| 版本 | `kh_document_version` | `UNIQUE(document_id, version)` |
| 通知 | `kh_notification` | `type`、`is_read`、部分索引未读 |

## 统一建模习惯

```sql
id BIGINT PRIMARY KEY,                              -- 雪花
created_at TIMESTAMP NOT NULL DEFAULT NOW(),
deleted BOOLEAN NOT NULL DEFAULT false,             -- 软删除
parent_id BIGINT NOT NULL DEFAULT 0                 -- 树根用 0，不用 NULL
```

**为什么根用 0**：`parent_id` 允许 `NOT NULL`，查询不用处理 `NULL` 分支；代价是没有外键约束（分类是配置数据，级联删除会误伤文档归属）。

## ① 分类：树在应用层拼

```ts
async tree(): Promise<CategoryNode[]> {
  // 一次全量取回（配置数据量小），在内存里按 parent_id 组树
}
```

**为什么不用递归 SQL**：分类是配置数据，量级几百条，一次全取 + 内存组树比多次查询更快也更简单。

`namesByIds()` 解决列表页的 N+1：

```ts
const names = await this.categories.namesByIds(ids);   // 一次 IN 查询
items.map((item) => ({ ...item, categoryName: names.get(item.categoryId) ?? null }));
```

## ② 互动：计数与通知

```ts
toggleLike(documentId, user)      // 有则删、无则插，返回新的 liked 状态与计数
toggleFavorite(...)               // 同上
addComment(documentId, dto, user) // 写评论 + 通知作者
```

`requireReadable(documentId, user)` 复用 v15 的可见性规则：**看不到的文档不能点赞/评论**——否则会变成权限绕过（通过互动接口探测文档是否存在）。

`notifyAuthor()` 在互动后写通知，**作者自己操作自己不通知**。

## ③ 分享：四要素 + 两段式访问

```ts
const token = randomBytes(9).toString('base64url').slice(0, 12);  // 12 字符，不可猜
const expireAt = dto.expireDays ? new Date(Date.now() + dto.expireDays * 864e5) : null;
const passwordHash = dto.password ? await hash(dto.password, 10) : null;
```

| 字段 | 语义 |
|---|---|
| `token` | 链接短码，`UNIQUE`，`/share/{token}` |
| `expire_at` | `NULL` = 长期有效 |
| `revoked` | 主动撤销 |
| `require_password` + `password_hash` | 密码门，**只存哈希、绝不回显** |

**访问拆成两个接口**：

```
GET  /share/:code            preview()  只返回元信息（要不要密码、标题）
POST /share/:code/access     access()   带密码校验 → 返回正文
```

**为什么拆**：有密码的链接，未验证前连正文都不该下发；只返回"需要密码"这一条事实。

**失效统一文案**：过期、撤销、文档未发布，全部返回同一句"分享链接不存在或已关闭"——不区分状态，避免泄漏"这个链接存在过"。

`requireShareable()`：只有**已发布**文档、且**作者或管理员**才能创建分享。

## ④ 版本：回滚也是新版本

```ts
recordContentChange({ documentId, previous, next })
  ├─ insertIgnore(previous)        // 首次记录时补一条基线
  └─ insertIgnore(next)            // 版本号来自内容文档的 version 计数
```

- 版本号来自 Mongo 正文文档的 `version` 字段（`oldVersion + 1`），不是 `MAX(version)+1` 查询；
- `insertIgnore` 用 `ON CONFLICT DO NOTHING` 兜底唯一键，**重复写入不报错**；
- 回滚 = 把旧正文写成一条**新版本**，历史全保留。

> 为什么不做覆盖：覆盖会丢掉"回滚过"这件事本身，也无法再回滚回去。

## ⑤ 通知

```ts
notify({ userId, type, title, content, documentId?, senderId?, senderName? })
list(userId, page, pageSize)
unreadCount(userId)
markRead(userId, id)
markAllRead(userId)
broadcast(dto, sender)     // 群发给所有用户（管理员）
```

未读数靠**部分索引**支撑：

```sql
CREATE INDEX IF NOT EXISTS idx_kh_notification_unread
    ON kh_notification(user_id) WHERE is_read = false;
```

只索引未读行，索引小、命中快——比全表 `is_read = false` 扫描好得多。

`init.sql` 只在**空数据卷首次启动**时执行。已有库必须单独跑：

[`init-scripts/postgresql/migrations/2026-11-18-product-experience.sql`](docs/../init-scripts/postgresql/migrations/2026-11-18-product-experience.sql)

内容包括：

1. 7 张表的 `CREATE TABLE IF NOT EXISTS`
2. 全部索引（含未读部分索引）
3. 3 条默认分类
4. 3 个权限码（`document:category`、`document:category:query`、`document:version`）
5. **给 ROLE_ADMIN 授权**——否则新菜单不会出现

```bash
docker exec -i knowledge_hub_postgres psql -U user -d knowledge_hub \
  -f /docker-entrypoint-initdb.d/migrations/2026-11-18-product-experience.sql
```

全部幂等，可重复执行。

## 易错点

| 坑 | 说明 |
|---|---|
| 只改 init.sql | 已有库不会自动建表，必须跑增量脚本 |
| 新权限码没授权 | 按钮/菜单不出现，看起来像"功能没做" |
| 回滚当成覆盖 | 历史丢失，无法再回滚 |
| 版本号用 `MAX+1` | 并发下会撞唯一键；应从内容文档的 version 递增 + `ON CONFLICT DO NOTHING` |
| 分享不校验可读性 | 通过分享页泄露无权文档 |
| 密码明文存 | 必须 bcrypt 哈希 |
| `expire_at` 存 0 而不是 NULL | 立即过期 |
| 失效文案区分状态 | 泄漏"链接存在过" |
| 分类删除直接删 | 文档会指向不存在的分类，应校验引用或改挂载 |
| 互动不校验文档可见性 | 可用来探测文档是否存在 |
| 评论冗余 `user_name` | 改名后历史评论不同步（用读性能换的） |
| 通知同步写 | 高频互动会拖慢主链路，应异步 |

## 主动回忆

1. **为什么分类根节点用 `parent_id = 0` 而不是 `NULL`？**
   可以让列保持 `NOT NULL`，查询少一个分支；代价是没有外键约束，删除父分类不会级联，需要在 Service 层校验是否还有文档引用。

2. **分享链接怎么保证安全？**
   不可猜 token（12 字符 base64url）+ 密码只存 bcrypt 哈希 + 有效期 + 可撤销 + 失效统一文案；访问拆成 preview/access 两段，未验密码不下发正文。

3. **回滚为什么要生成新版本而不是覆盖？**
   可追溯：覆盖会丢掉"回滚过"这件事，也无法回滚回去。版本表是只追加的日志。

4. **版本号为什么不用 `MAX(version)+1`？**
   并发下两个请求会算出同一个号撞唯一键；改用内容文档上的 `version` 递增，并用 `ON CONFLICT DO NOTHING` 兜底。

5. **未读通知为什么用部分索引？**
   `WHERE is_read = false` 的部分索引只包含未读行，索引小、更新成本低，正好匹配"查未读数"这个高频操作。
