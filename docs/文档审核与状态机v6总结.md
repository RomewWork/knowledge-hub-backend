# 文档审核与状态机 v6 总结

> 课程 54 · 代码基线 `ai-agent-code/knowledge/knowledge-hub-backend`（v6 改动在工作区）
> 整理时间：2026-10-30

## 一句话

**「发布」不再等于「上线」**：需审核时 `publish` 只是提审，真正建索引发生在 `approveReview`。新增第四态 `PendingReview` + 审核流水表，把状态与三路索引联动起来。

## 状态机

```
Draft(0) ──提交──► PendingReview(3) ──通过──► Published(1) ──归档──► Archived(2)
   ▲                    │                        │                     │
   └──── 驳回 ───────────┘                        └──保存草稿──► Draft ◄┘(重新发布)
                        Published ──再提交──► PendingReview（先清索引）
```

| 状态 | 值 | 可检索 | 说明 |
|---|---:|---|---|
| Draft | 0 | ❌ | 草稿 |
| Published | 1 | ✅ | 三路索引都有 |
| Archived | 2 | ❌ | 保留正文，清索引 |
| PendingReview | 3 | ❌ | 评审中，不进索引 |

## 状态 × 索引 联动（核心）

| 动作 | 状态变化 | 索引动作 |
|---|---|---|
| 提审（来自 Draft） | 0 → 3 | 无 |
| 提审（来自 Published） | 1 → 3 | **先清** RAG/Search/KG |
| 审核通过 | 3 → 1 | **重建**三路索引 |
| 审核驳回 | 3 → 0 | 无（本就没索引） |
| 免审发布 | * → 1 | 重建索引 |
| 归档 | 1 → 2 | 清索引 |
| 保存草稿 | 1 → 0 | 清索引 |
| 软删除 | — | 仅 Published 才清（`remove()`） |
| 改正文（已发布） | 1 → 1 | 免审模式直接重建；需审模式不动（等下轮提审） |

## 接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/documents/reviews/tasks?status=` | `pending`(默认) / `approved` / `rejected` |
| GET | `/documents/reviews/tasks/pending-count` | 待办数 |
| POST | `/documents/:id/reviews/submit` | 提交审核 |
| GET | `/documents/:id/reviews/current` | 当前待审任务 |
| GET | `/documents/:id/reviews/history` | 全部审核记录 |
| POST | `/documents/reviews/tasks/:taskId/approve` | 通过 |
| POST | `/documents/reviews/tasks/:taskId/reject` | 驳回（`reviewComment` 必填） |
| PUT | `/documents/:id/publish` | 分流：需审 → 提审；免审 → 直接发布 |
| PUT | `/documents/:id/archive` | 归档 |
| PUT | `/documents/:id/save-draft` | 已发布 → 草稿 |

## 四条规则

1. **同一文档只能有 1 条待审记录**：提交前查 `review_result IS NULL`，有则 400。
2. **待审期间禁止改正文/标题**：`canEditContent(PendingReview) === false`。
3. **驳回必须填意见**：`reviewComment` 空 → 400。
4. **待审不进索引**：提审即下线，通过才重新上线。

## 两个坑

1. **路由顺序**：`GET reviews/tasks` 必须注册在 `GET :id` 之前，否则被 `:id` 吃掉（代码里有注释）。
2. **建表要迁移**：`init.sql` 只在空库跑一次，老库新增 `kh_document_review` 不生效 —— 必须用 migration（TypeORM `migration:run`）。

## 验收

```bash
# 提审 → 待办 → 通过
curl -X POST localhost:3000/documents/$ID/reviews/submit
curl        localhost:3000/documents/reviews/tasks
curl -X POST localhost:3000/documents/reviews/tasks/$RID/approve

# 驳回路径
curl -X POST localhost:3000/documents/reviews/tasks/$RID/reject \
  -H 'Content-Type: application/json' -d '{"reviewComment":"内容不完整"}'
```

| 检查点 | 期望 |
|---|---|
| 提审后 `status` | 3 |
| 提审后查 ES / Neo4j | **查不到**该文档 |
| 通过后 `status` | 1，`publishTime` 更新 |
| 通过后查 `kh_document` / `kh_chunk` / Neo4j | 三条都有 |
| 驳回后 `status` | 0 |
| 重复提审 | 400「该文档已有待审核任务」 |
| 待审时 PATCH 正文 | 400 |
| `DOCUMENT_REQUIRE_APPROVAL=false` | `publish` 直接发布，不走审核 |

## 主动回忆

1. **为什么提审要清索引？**
   待审文档内容可能被改，旧索引一旦被召回就是错误答案；且「评审中」语义上不该对外可见。通过时按最新正文重建，保证索引与最终稿一致。

2. **为什么审核记录用独立流水表，而不是在 `kh_document` 加字段？**
   一次提审一条记录，天然支持「多轮审核历史」；`before_status` 保留提审前状态便于回溯；待办列表就是一个 `review_result IS NULL` 的查询，加 partial index 即可，不污染主表。

3. **`DocumentStatus` 为什么要从 entity 挪到独立文件？**
   状态流转规则（谁能发布/编辑/归档/提审）是业务规则，属于领域层；entity 只该管表映射。挪出去后 `document.service` 和 `document-review.service` 共用同一套规则，不会各写一份 if-else 而漂移。
