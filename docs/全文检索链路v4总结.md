# 全文检索链路 v4 总结（发布 → MQ 快照 → ES kh_document）

> 对应课程：52 企业级知识库项目 · 全文检索链路（RAG 链路的前情见 `docs/异步RAG流水线v3总结.md`）
> 代码基线：`ai-agent-code/knowledge/knowledge-hub-backend`（学习项目，**v4 在工作区，尚未提交**；仓库最后一次提交是 `db8e2eb feat: v3`）
> 技术栈：Nest + amqp-connection-manager/amqplib + @elastic/elasticsearch 8.17 + RabbitMQ 3.13 + ES 8.17（镜像装了 IK）+ PG16/MongoDB 7
> 整理时间：2026-10-26

---

## 0. 一页速览

v4 在 v3 的 RAG 链路上**并出第二条派生索引**：发布时多投一条 Search 事件，消息里**直接带文档快照**，消费者不做切分、不做 embedding、不回查任何库，只是把快照 upsert 进 ES `kh_document`。

一个关键认知先行：**v4 只做了「写」这一半。** `kh_document` 还没有任何查询接口，BM25 检索引擎侧尚未接入 —— 所以本讲交付的是**全文索引链路**，不是「全文检索 API」。

| 维度 | 结论 |
| --- | --- |
| 入口 | `PUT /documents/:id/publish`（无审核、无鉴权，见 54/55） |
| 新增触发点 | `afterPublish()` 里 **RAG + Search 两条消息**；未新增 HTTP 接口 |
| 交换机 | 新增 `search.index.exchange`（`topic`, durable），与 `rag.reindex.exchange` 并列 |
| 队列 / 路由键 | `kh.search.index.queue` / `search.index.document`（INDEX）、`search.index.delete`（DELETE） |
| 消息体 | `{ taskId, type:'INDEX', documentId, document:{...15 个字段} }`，正文只截 **1000 字符** |
| 消费入口 | `DocumentPipelineConsumer.handleSearch()` → `PipelineOrchestrator.handleSearchIndex()` |
| 编排 | **无编排**：INDEX 直接写、DELETE 直接删，只有 17 行 |
| 索引 | ES `kh_document`，**一条记录 = 一篇文档**，`_id = documentId` |
| 粒度 | 文档级（`kh_document`）vs 块级（`kh_chunk`），二者互补，见 §6 |
| 幂等 | 稳定 `_id = documentId` → `index` 覆盖写；删除对 404 视为成功 |
| 降级 | `ELASTICSEARCH_ENABLED=false` 或启动时连不上 → `es=null`，**永久跳过写入**并打 warn |
| 未落地 | 检索查询接口、IK 分词配置、删除事件的调用方、ack/重试/DLQ、版本号、索引状态表 |

```
PUT /documents/:id/publish
  │
  ├─ PG: status=Published, publish_time=now()          ← 事实源（同步）
  ├─ Mongo: 读正文 content                             ← 一次读，两处用
  │
  └─ afterPublish(saved, content)
        ├─ triggerRagReindex(id)    ──► rag.reindex.exchange ──rk: by_ids──► kh.rag.reindex.queue
        │                                                                    └─► 分块 → 嵌入 → kh_chunk
        └─ triggerSearchIndex(doc, content)
              buildSearchIndexData()  ← 截断 1000 字
              ──► search.index.exchange ──rk: search.index.document──► kh.search.index.queue
                                                                            └─► kh_document（upsert）
```

### 0.1 与 v3 的差异（增量清单）

| 类别 | v3 | v4 新增 |
| --- | --- | --- |
| 交换机 | `rag.reindex.exchange` | `+ search.index.exchange`（topic, durable） |
| 队列 | `kh.rag.reindex.queue` | `+ kh.search.index.queue` |
| 路由键 | `rag.reindex.by_ids` | `+ rag.reindex.delete`、`+ search.index.document`、`+ search.index.delete` |
| 消息类型 | `ReindexMessage`（`BY_DOC_IDS`） | `+ SearchIndexMessage`（`INDEX`/`DELETE`）、`ReindexType += DELETE_BY_DOC_IDS` |
| 新增文件 | — | `src/pipeline/search-index.service.ts`（121 行，唯一新文件） |
| 生产端 | `afterPublish(document)` 投 1 条 | `afterPublish(document, content)` 投 2 条；`+ afterUnpublish()`（**未被调用**） |
| 消费端 | 只注册 RAG 队列 | 构造器里多注册一个 `SEARCH_INDEX_QUEUE` handler |
| 编排 | `handleRagReindex()` | `+ handleSearchIndex()`；RAG 分支多一个 `DELETE_BY_DOC_IDS` 早返回 |
| 编排器依赖 | 4 个 | `+ SearchIndexService` |
| 索引 | `kh_chunk`（块 + 向量） | `+ kh_document`（整篇 + 元数据） |
| 数据流 | 发布 → 索引（一路） | 发布 → 索引（两路并行，互不阻塞） |

**v4 没有动的**：`rabbitmq.service.ts` 的 ack 逻辑（仍然只 `nack`、不 `ack`）、分块参数、embedding、`kh_chunk` mapping、`document.service.ts` 的 `remove()/update()`（既不清理也不重建索引）。

### 0.2 一句话结论

**v4 用「消息带快照」把全文索引从 RAG 链路里解耦出来，写路径干净且天然幂等（`_id = documentId`）；但它只完成了链路的一半 —— 检索侧没有查询接口、分词没配 IK、下线不清理、消费不 ack。** 换言之：索引建好了，还查不了；删得掉单条，但没人触发删除。

## 2. MQ 拓扑：一条 exchange 变两条

### 2.1 拓扑（`src/mq/mq.constans.ts` + `rabbitmq.service.ts#assertTopology`）

| 对象 | 名称 | 参数 | 作用 |
| --- | --- | --- | --- |
| Exchange | `search.index.exchange` | `topic`, durable | 接收文档级全文索引事件 |
| Queue | `kh.search.index.queue` | durable | 本服务消费 |
| Binding | `search.index.document` | — | `INDEX`：写入/覆盖文档快照 |
| Binding | `search.index.delete` | — | `DELETE`：按文档 ID 移除 |
| Exchange | `rag.reindex.exchange` | `topic`, durable（v3 已有） | RAG 重建 |
| Binding（新增） | `rag.reindex.delete` | — | `DELETE_BY_DOC_IDS`：清理向量块 |

**设计取向**：Search 和 RAG **不共用 exchange**，各建一条。理由（也是面试点）：

1. **隔离故障域**：Search 消费的是 ES 写入；RAG 消费的是 embedding API。共用交换机时，一条链路的积压/阻塞会通过同一队列传导；分开后可以独立 prefetch、独立扩缩容、独立 DLQ。
2. **消息形态不同**：RAG 消息只带 ID（小），Search 消息带快照（大）。同队列会让「大消息」拖慢「小消息」的处理节奏。
3. **独立演进**：以后给 Search 换 mapping、加 IK、加同义词，不影响 RAG 的消费速率。

代价是拓扑声明多两行、运维多看一个队列。

### 2.2 一个细节：日志仍然只报 RAG

```ts
this.logger.log('RabbitMQ 拓扑已声明（RAG）');   // 实际声明了 2 个 exchange、2 个队列
```

日志文案没跟着改。**排障时别被这句话骗了** —— 看到它不代表 Search 拓扑没声明。

## 3. 生产端：快照是怎么组装的

### 3.1 `afterPublish()` 的双投递

```ts
async afterPublish(document: DocumentEntity, content?: string | null) {
  await Promise.all([
    await this.triggerRagReindex(document.id),        // ← 注意这里的 await
    await this.triggerSearchIndex(document, content), // ← 以及这里
  ]);
}
```

**代码异味（值得记）**：数组字面量里的 `await` 会**先串行执行完**两个 promise，再把已完成的 promise 交给 `Promise.all`。所以这里实际是「串行投递」，不是并行。对比同文件的 `afterUnpublish()`：

```ts
await Promise.all([this.triggerRagDelete(documentId), this.triggerSearchDelete(documentId)]);  // 真并行
```

两者写法不一致。影响很小（`channel.publish` 在 confirm channel 上是一次 broker 确认，量级毫秒），但**语义错误会误导后来人**：注释写「并行投递」，代码是串行。正确写法是把 `await` 去掉，只留 `Promise.all([...])`。

### 3.2 `buildSearchIndexData()`：写进 ES 的 15 个字段

| 字段 | 来源 | ES 里声明的类型 | 说明 |
| --- | --- | --- | --- |
| `id` | `document.id` | `keyword` | 与 `_id` 冗余，便于聚合/回查 |
| `title` | 同名字段 | `text` | 标题，BM25 主权重字段之一 |
| `summary` | 同名字段，`?? null` | `text` | 摘要 |
| `content` | **截断 1000 字符** | `text` | 正文前缀，不是全文 |
| `categoryId` | `?? null` | `keyword` | 分类过滤 |
| `tags` | `?? null`（数组） | `keyword` | 标签过滤 |
| `status` | 同名字段 | `integer` | 发布时状态（归档不会更新，见 §8） |
| `isPublic` | 同名字段 | **未声明** | 动态映射（`boolean`） |
| `viewCount` / `likeCount` / `commentCount` | 同名字段 | **未声明** | 动态映射（`long`），可做业务排序 |
| `authorId` | `?? null` | `keyword` | 作者过滤（55 用） |
| `publishTime` | `?.toISOString() ?? null` | `date` | 时间过滤/排序 |
| `createdAt` / `updatedAt` | `?.toISOString() ?? null` | **未声明** | 动态映射（`date`） |

两个要点：

- **`?? null` 全军覆没**：`null` 写进 ES 会被当作「该字段无值」，可以正常 `exists` 判断，但**不能参与排序/聚合**（会被跳过）。想按 `viewCount` 排序时要 `missing` 兜底。
- **未声明字段靠动态映射**：`kh_document` 的 mapping 里只写了 9 个字段，其余 6 个由 ES 首次写入时自动推断。因为 `dynamic` 默认 `true`，所以能跑，但**类型由第一批数据决定** —— 如果 `viewCount` 第一次写进来是 `null`，ES 会跳过推断，等第一次有整数时才建 `long`。这是「隐式 schema」的典型风险，生产应显式声明并考虑 `dynamic: strict`。

### 3.3 为什么正文只截 1000 字符

- **控制消息体积**：正文几十 KB ~ MB，塞进 broker 会拖慢投递、占内存、放大重投成本。1000 字符 ≈ 一条几 KB 的消息。
- **够用**：文档级全文索引的目标是「**这篇文档是否相关**」，标题 + 摘要 + 正文前缀已经能覆盖绝大多数关键词命中；真正的细粒度召回由 `kh_chunk` 承担（§6）。
- **代价**：正文 1000 字以后的词在这条索引里**搜不到**。一篇 5 万字的制度文档，只有开头 1000 字参与文档级 BM25 —— 这是「快照」方案的必然取舍，也是最容易在验收时被误判为 bug 的点。

### 3.4 投递失败的口径（沿用 v3）

`triggerSearchIndex()` 拿到 `ok=false` 只 `logger.log`；`document.service.ts` 外层还有 try/catch 兜底：

```ts
try { await this.pipelinePublisher.afterPublish(saved, content); }
catch { this.logger.warn('发布后管线投递失败（不影响发布）'); }
```

**三处日志语义要分清**：

| 层 | 条件 | 后果 |
| --- | --- | --- |
| `RabbitMqService.publish()` | MQ 未连接/抛错 | 返回 `false`，打 warn |
| `triggerSearchIndex()` | `ok=false` | 打 log「投递失败」，**不重试** |
| `document.service#publish` | `afterPublish` 抛错 | 打 warn，发布仍成功 |

即：**发布成功 ≠ 索引成功 ≠ 消息已入队**。三层各自降级，没有任何补偿。

## 4. 消费端：Search 分支几乎无逻辑

```ts
// document-pipeline.consumer.ts
constructor(rabbit, orchestrator) {
  this.rabbit.registerHandler(RAG_REINDEX_QUEUE,    (msg) => this.handleRag(msg));
  this.rabbit.registerHandler(SEARCH_INDEX_QUEUE, (msg) => this.handleSearch(msg));  // v4 新增
}

private async handleSearch(msg) {
  const body = this.parseJson<SearchIndexMessage>(msg);
  this.logger.log(`[Search] type=${body.type}, taskId=${body.taskId}, documentId=${body.documentId}`);
  await this.orchestrator.handleSearchIndex(body.type, body.documentId, body.document);
}
```

```ts
// pipeline.orchestrator.ts —— 全部逻辑就这 17 行
async handleSearchIndex(type, documentId, document?) {
  if (type === 'DELETE') { await this.searchIndexService.deleteDocument(documentId); return; }
  if (type === 'INDEX') {
    if (!document) { this.logger.warn(`Search INDEX 消息缺少 document 快照：documentId=${documentId}`); return; }
    await this.searchIndexService.indexDocument(document);
    return;
  }
  this.logger.warn(`忽略未支持的 Search 消息：type=${type}`);
}
```

**「无编排」正是这条链路的设计要点**：快照自带一切，消费者不需要 PG、不需要 Mongo、不需要分块、不需要 embedding。所以它的故障面比 RAG 小一个数量级 —— 只有一个外部依赖：ES。

与 RAG 分支的三个不对称（对比记忆）：

| 维度 | RAG 分支 | Search 分支 |
| --- | --- | --- |
| 依赖 | PG + Mongo + embedding API + ES | 仅 ES |
| 异常处理 | `reindexOne` 每篇 `try/catch` 吞掉，继续下一篇 | **不捕获**，直接冒泡到 consumer |
| 失败后果 | 单篇失败静默（只留 error 日志） | 冒泡 → `nack(requeue=false)` → **消息丢弃** |
| 缺数据时 | 按 ID 查不到就 `continue` | 快照缺失 → warn + return（无索引，无告警） |

即：**RAG 是「悄悄错」，Search 是「响亮地丢」。** 后者听着更糟，但从可观测性看，响亮地丢至少还能在日志里看到 `nack`。

## 5. 索引层：`kh_document`

### 5.1 mapping（`search-index.service.ts#ensureEsIndex`）

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `id` | `keyword` | 与 `_id` 冗余 |
| `title` / `summary` / `content` | `text` | BM25 三个主字段（**默认 standard 分词**） |
| `tags` | `keyword` | 标签精确过滤 |
| `status` | `integer` | 状态过滤 |
| `categoryId` / `authorId` | `keyword` | 分类/权限过滤 |
| `publishTime` | `date` | 时间过滤/排序 |

索引级参数：**没有显式设置** —— 用 ES 默认（1 分片、1 副本、`refresh_interval: 1s`）。与 `kh_chunk` 显式写的「1 分片 0 副本」不一致，本地开发时副本会一直是 unassigned（单节点集群），日志里能看到 yellow。生产要显式声明。

### 5.2 写路径

```ts
await this.es.index({
  index: 'kh_document',
  id: String(doc.id),                          // ← 稳定 _id = documentId
  document: { ...doc, indexedAt: new Date().toISOString() },
  refresh: true,                               // ← 每次写都立刻可见
});
```

- **`_id = documentId`** 是全文索引幂等的全部秘密：同一篇文档重复发布，ES 只是覆盖同一条记录，**永远不会翻倍**。
- `indexedAt` 由**消费者**在写入时刻打，而不是发布时刻 —— 所以它能真实反映「这条索引什么时候进 ES」，是判断索引新鲜度的唯一依据（`indexedAt >= publishTime` 才算追上）。
- `refresh: true`：测试友好（写完立刻能 `_search` 到），生产应该关掉或把 `refresh_interval` 调大，否则每次写都触发一次 refresh，吞吐会掉。
- **`id` 用 `String()`**：雪花 ID 是 64 位整数，转字符串避免 JS 精度丢失 —— 与 `kh_chunk` 里 `document_id` 用 `keyword` 是同一个理由。

### 5.3 删除路径

```ts
try {
  await this.es.delete({ index: 'kh_document', id: documentId, refresh: true });
} catch (error) {
  if (!message.includes('404')) this.logger.warn(`ES 删除失败：documentId=${documentId}, ${message}`);
}
this.logger.log(`搜索索引已删除：documentId=${documentId}`);   // ← 无论成功失败都打印
```

三个问题：

1. **404 视为成功**：删一条不存在的文档不报错 —— 这是**幂等删除的正确做法**（重复删除不产生副作用），值得肯定。
2. **非 404 异常被吞**：ES 挂了、mapping 冲突、权限错误，全都只留一行 warn，然后继续。
3. **最后一行日志无条件打印**「已删除」：即使删除真的失败了，日志也会说成功。**排障时这行日志没有可信度**，要看前面有没有 warn。

对比 `kh_chunk` 的删除（`deleteByDocId`）：忽略 `index_not_found`，其余 `logger.error` 后同样吞掉 —— 两条链路的删除**都是「尽力而为」语义**。

### 5.4 ES 不可用时的降级

`onModuleInit` 里 `cluster.health()` 失败 → `this.es = null`，此后所有写/删都走 `if (!this.es) { warn; return; }`。

**这是一次性降级，进程内永不恢复**：ES 晚于服务启动 30 秒，整个生命周期内全文索引都是空的，只能重启服务。生产要给 ES client 加重试/健康探测，或按调用懒恢复（每次写入前 `if (!es) tryReconnect()`）。

`ELASTICSEARCH_ENABLED=false` 是另一个开关，效果一样但语义更明确：**「我知道我不想要全文索引」** vs 「ES 挂了」。二者在日志里都是 warn，排障时容易混淆 —— 建议区分文案。

## 6. 粒度：`kh_document` vs `kh_chunk`（本讲核心）

同一个 ES 集群里，两套索引服务两种检索需求。**它们的差别不是「存的字段多不多」，而是「一条记录代表什么」**。

| 维度 | `kh_document`（v4） | `kh_chunk`（v3） |
| --- | --- | --- |
| **一条记录 =** | **一篇文档** | **一个文本块**（512 token ≈ 1024 字符) |
| `_id` | `documentId`（1 条/文档） | `sha256(documentId:chunkIndex)`（N 条/文档） |
| 记录数 | `= 文档数` | `= 总块数`（一篇 50 页文档可能 200 块） |
| 内容完整性 | 标题 + 摘要 + **正文前 1000 字** | 正文**全量**切分，含 heading 前缀 |
| 向量 | ❌ 无 | ✅ `dense_vector(dims=1024)` |
| 检索方式 | BM25 关键词（规划中） | kNN 向量 + BM25（混合） |
| 召回语义 | 「**哪些文档**提到了 X」 | 「**哪一段**在讲 X」 |
| 命中后要做什么 | 回 PG/Mongo 取正文再展示 | 可直接作为 LLM 上下文 / 高亮 |
| 排序可用信号 | 浏览量、点赞、发布时间、标题权重 | 相似度分数、chunk 顺序 |
| 删除成本 | 1 次 `delete` by `_id` | 1 次 `deleteByQuery(document_id)`（N 条） |
| 存储量级 | 小（≈ 文档数 × 几 KB） | 大（≈ 块数 × (正文 + 4KB 向量)） |

### 6.1 为什么要两套，而不是一套

- **召回单位不同**：用户搜「年假怎么算」，需要的是**那一段制度原文**（chunk），而不是「员工手册.pdf 这篇文档」；但用户浏览知识库列表、按标题搜文档时，需要的是**文档**（document）。
- **成本不同**：`kh_chunk` 每条带 1024 维向量（float32 ≈ 4 KB），10 万块就是 400 MB 向量数据；`kh_document` 无向量，10 万文档也就几百 MB 文本。**全文索引便宜，向量索引贵**，不该混在一起。
- **更新粒度不同**：改一个段落，`kh_chunk` 要重建该文档全部块，`kh_document` 只需覆盖一条。
- **权限过滤不同**：`kh_chunk` 要带 `team_id`/`author_id` 做块级过滤（55），`kh_document` 过滤文档级即可。

### 6.2 两套索引的融合（下一步，不在 v4）

检索侧的典型做法是**双路召回 + 融合**：

```
query ──┬─► kh_document BM25 ──► 文档级候选（召回"哪几篇"）
        └─► kh_chunk kNN/BM25 ──► 块级候选（召回"哪几段"）
                │
                └─► RRF / Rerank 融合 ──► 取 topN 上下文
                        │
                        └─ 块级结果按 document_id 聚合去重，再与文档级结果对齐
```

融合时要解决的第一个问题就是**粒度不对齐**：块级命中 5 条可能全属于同一篇文档，文档级命中 3 篇可能一篇都没进块级 topN。常见处理是「块级结果按 `document_id` 折叠（collapse）后再与文档级合并」—— 这属于 29（混合检索 + RRF/Rerank）的内容，v4 不做。

## 7. 为什么 Search 用快照，RAG/KG 按 ID 拉正文

这是课程 51/52 评论区的高频问题，也是本讲最值得背下来的一段。

| 链路 | 消息内容 | 消费者做的事 | 为什么这么设计 |
| --- | --- | --- | --- |
| RAG | 只传 `documentIds` | 回查 PG 元数据 + Mongo 正文 → 分块 → 嵌入 | **必须读全文**（要切分，1000 字不够）；正文太大不能进消息；「重建当前版本」比「复现发布那一刻」更重要 |
| KG（53） | 只传 `documentId` | 回查正文 → LLM 抽实体 | 同上，且抽取耗时秒级~分钟级，消息必须小 |
| **Search** | **元数据 + 正文快照** | **不回查，直接写 ES** | 全文索引要的就是「**发布那一刻的视图**」；快照让消费者零依赖，故障面最小 |

### 7.1 三个正面理由

1. **语义精确**：Search 索引的是「这一版文档」。快照让「版本」这个概念**落在消息里**，消费者写进去的就是发布那一刻的事实，不会因为期间正文被改而写出一个「半新半旧」的索引。
2. **少一次跨库读**：消费者不碰 PG、不碰 Mongo，`handleSearchIndex` 只有 17 行，连数据库连接池都不需要。**依赖越少，消费越快、越可靠**。
3. **可重放**：同一条消息重投，写进去的内容完全一样（快照在消息里），重放语义是确定的。而「按 ID 回查」的消息重放时，读到的是**当前**正文 —— 重放结果取决于重放时机。

### 7.2 三个代价（必须一起说）

1. **消息变大**：正文截 1000 字后仍可能几 KB，是 RAG 消息（约 100 字节）的几十倍。批量导入时 broker 内存和网络压力明显。
2. **正文不全**：1000 字以后的词搜不到（§3.3）。若业务要求全文可搜，就得改成「按 ID 回查」或「消息只带版本号 + 消费时读全文」。
3. **快照会陈旧（最危险）**：`update()` 改正文**不触发重新发布** → `kh_document` 里永远是旧正文。这不是「暂时不一致」，是**永久不一致**，直到下次发布。RAG 链路同样有这个问题，但 Search 因为「不对比事实源」而更隐蔽 —— 用户搜到旧内容、点进去看到新正文，会认为是搜索错了。

> 一句话：**快照换来确定性，回查换来新鲜度。** 选哪个，取决于「索引允许比事实源旧多久」这个业务问题，而不是技术偏好。

## 8. 删除链路与幂等

### 8.1 设计意图（`afterUnpublish`）

```ts
async afterUnpublish(documentId: string) {
  await Promise.all([this.triggerRagDelete(documentId), this.triggerSearchDelete(documentId)]);
}
```

意图很清楚：文档下线 → 并行通知两条链路清理，RAG 用 `DELETE_BY_DOC_IDS`，Search 用 `DELETE`。

### 8.2 现状：这个函数**没有任何调用方**

`grep -r "afterUnpublish" src/` 只命中它的定义。`document.service.ts#remove()` 是：

```ts
doc.deleted = true;
await this.em.save(doc);
await this.contentModel.updateOne({ _id: doc.contentId }, { $set: { deleted: true } });
return { id, deleted: true };     // ← 到此为止，没有任何 MQ 投递
```

**后果**：文档软删了，`kh_document` 和 `kh_chunk` 里都还留着完整记录。检索侧一旦接上查询接口，**已删除的文档会立刻被召回**。

同理，`update()` 改正文、`PATCH status=2` 归档，也都不会有任何索引动作。

### 8.3 幂等矩阵（v4 真实行为）

| 场景 | 链路 | 动作 | 幂等 | 说明 |
| --- | --- | --- | --- | --- |
| 同一 INDEX 消息重投 | Search | `index` 同 `_id` 覆盖 | ✅ | 结果与投一次相同 |
| 已发布再点发布 | Search | 同上 | ✅ | 天生幂等 |
| 并发两条 INDEX（旧快照后到） | Search | 后写覆盖先写 | ❌ | **无版本比较**，旧内容可能盖掉新内容 |
| 改正文不重新发布 | Search | 无事件 | ❌ | 索引永久停在旧版本 |
| 删除文档 | Search | **无事件** | ❌ | 幽灵记录常驻 |
| 归档 `status=2` | Search | 无事件 | ❌ | ES 里 `status` 仍是 1 |
| DELETE 消息重投 | Search | `delete` 同 `_id` | ✅ | 第二次 404 → 视为成功 |
| DELETE 到不存在的文档 | Search | 404 被吞 | ✅ | 幂等删除的正确语义 |
| DELETE 遇真失败 | Search | warn 后吞掉 | ⚠️ | 日志仍说「已删除」，无法感知 |
| 消费成功 | Search | **不 ack** | ⚠️ | unacked 堆积，重启重投 |
| 快照缺失 | Search | warn + return | ⚠️ | 无索引、无告警，消息实际丢弃 |
| ES 写入抛错 | Search | 冒泡 → `nack(requeue=false)` | ❌ | 无 DLQ，消息消失 |
| MQ 投递失败 | 生产端 | log 后放弃 | ❌ | 无 outbox |

### 8.4 幂等的三层防线（该怎么做）

**第一层：稳定键（已有，做对了）**

- `kh_document` 的 `_id = documentId` → 覆盖写，天然幂等。
- 删除对 404 幂等。

**第二层：顺序保护（缺）**

- 没有 `version` 字段，ES 也不比较版本 → 消息乱序时旧覆盖新。
- 补法：消息带 `version`（PG 加列或用 `updated_at` 毫秒），写入用 `if_seq_no`/`if_primary_term` 条件更新，或写脚本比较 `version` 后决定是否 `noop`。

**第三层：终态收敛（缺）**

- 删除/归档没有事件 → 靠「查询侧过滤 `deleted`/`status`」兜底（治标）+ 定时对账（治本）。
- 补法：`remove()` / `update(status)` / `update(content)` 都调 `afterUnpublish` 或新的 `afterUpdate`；每小时对账 `PG Published 文档集` 与 `kh_document 文档集` 的差集，多删少补。

### 8.5 一个反直觉的结论

**「删除」比「写入」更需要幂等设计。** 写入幂等只会导致「重复计算」（浪费 embedding），删除不幂等会导致**「该删的没删」**（幽灵数据长期污染召回）或**「删了不该删的」**（误删）。而 v4 恰好把删除做成了**有幂等实现、无调用方**的半成品。

## 9. 缺口清单与 v5 待办

**P0（正确性/数据）**

1. `afterUnpublish()` 无调用方 → 删除/归档不清理索引，幽灵记录可被召回。
2. 检索查询接口不存在 → `kh_document` 只写不读，本讲交付的是「索引链路」不是「检索能力」。
3. `content` 未配 IK 分词 → `standard` 分词器把中文切成单字，BM25 相关性极差（镜像里的 IK 插件装了但没用上）。必须显式 `analyzer: 'ik_max_word', search_analyzer: 'ik_smart'`。
4. `update()` 改正文不触发重建 → 索引永久停在旧版本（RAG 与 Search 都受影响）。
5. 消费成功不 `ack` → unacked 堆积 + 重启全量重投（v3 遗留，v4 未修）。

**P1（一致性/可运维）**

6. 无 `version` 字段 → 并发/乱序时旧快照覆盖新快照。
7. `deleteDocument` 吞非 404 异常且无条件打印「已删除」→ 失败不可见。
8. ES 启动不可用 → `es=null` 永久降级，进程内不恢复。
9. `kh_document` 未显式设置分片/副本/刷新间隔 → 与 `kh_chunk` 配置不一致，单节点 yellow。
10. 未声明字段靠动态映射（`isPublic`/`viewCount`/...）→ 隐式 schema。
11. `Promise.all` 里带 `await` → 名为并行实为串行。
12. 无 DLQ/重试；Search 失败 `nack(requeue=false)` 直接丢。

**P2（工程卫生）**

13. 拓扑日志仍写「（RAG）」，漏报 Search。
14. `mq.constans.ts`（应为 `constants`）、`pipeline.messagets.ts`（应为 `messages`）文件名拼写。
15. `refresh: true` 写死 → 生产吞吐受损，应配置化。

**v5 建议顺序**：① 查询接口 + IK mapping（让链路可用）→ ② 删除/归档/更新事件接线（让数据正确）→ ③ ack + 重试 + DLQ（让失败可见可恢复）→ ④ version + 对账（让顺序与漂移可控）。

## 11. 主动回忆（完整版答案）

### Q1 `kh_document` 与 `kh_chunk` 的检索粒度有何区别？

**`kh_document` 的一条 = 一篇文档，回答「哪几篇相关」；`kh_chunk` 的一条 = 一个 512-token 块，回答「哪几段相关」。**

1. **主键与条数**：`kh_document._id = documentId`，一篇一条；`kh_chunk._id = sha256(documentId:chunkIndex)`，一篇 N 条。这个差别决定了一切下游行为。
2. **内容完整性**：`kh_document` 只有标题 + 摘要 + **正文前 1000 字**（消息体积所限）；`kh_chunk` 是正文**全量**切分，且每块带 heading 前缀，还额外存 1024 维向量。
3. **检索方式**：`kh_document` 只走 BM25 关键词（v4 连这个都还没接）；`kh_chunk` 走 kNN 向量 + BM25 混合。
4. **召回语义与后续动作**：文档级命中是「入口」—— 用户还要点进详情页，由 PG/Mongo 提供正文；块级命中是「答案」—— 可以直接塞进 LLM 上下文或前端高亮。所以 `kh_document` 可以"信息不全"，`kh_chunk` 必须"信息完整"。
5. **成本与更新**：`kh_document` 无向量、体量小、改一段只需覆盖一条；`kh_chunk` 每条带 4 KB 向量、体量大、改一段要重建全部块。
6. **融合时的坑**：两套索引粒度不对齐 —— 块级 top5 可能全属于同一篇，文档级 top3 可能一篇都没进块级榜。要按 `document_id` collapse 去重后再融合（RRF/Rerank，见 29）。

> 一句话：**`kh_document` 是「目录」，`kh_chunk` 是「正文段落」；目录便宜、覆盖广、但只有前 1000 字；段落贵、精确、能直接喂给模型。**

### Q2 为何 Search 可用快照而其他链路按 ID 拉正文？

**因为三条链路对「版本」和「正文规模」的要求完全不同：Search 要的是「发布那一刻的确定版本」，RAG/KG 要的是「当前版本的完整正文」。**

1. **正文规模**：RAG 要切分全文、KG 要抽全文实体，正文几十 KB ~ MB，**塞不进消息**（broker 内存、网络、重投成本都会爆）；Search 只要「能判断文档相关性」，标题 + 摘要 + 1000 字前缀足够，截断后只有几 KB。
2. **版本语义**：Search 索引「这一版」是合理的 —— 全文索引是给人看的入口，用户点进去看到最新正文即可，索引旧一点可以接受；RAG 分块必须反映当前正文，否则检索到的块和用户看到的正文对不上。**「按 ID 回查」天然拿到最新，「快照」天然冻结在发布那一刻。**
3. **依赖与故障面**：快照让 Search 消费者**零跨库依赖**（不碰 PG/Mongo），`handleSearchIndex` 只有 17 行，故障面 = ES 一个；RAG 消费者要 PG + Mongo + embedding API + ES 四个依赖。
4. **可重放性**：快照消息重投写入的内容完全确定；「按 ID 回查」的消息重投结果取决于重投时机（正文可能已变）。
5. **代价必须承认**：快照会陈旧 —— `update()` 改正文不重新发布时，`kh_document` 会**永久**停在旧内容；且 1000 字以后的词搜不到。RAG 的代价相反：慢、要在消费时多读一次库、且并发时可能读到"比消息更新"的正文（同样需要版本号）。

> 一句话：**快照换确定性与低依赖，回查换新鲜度与完整性。** Search 用前者，RAG/KG 用后者。

### Q3 删除链路怎样保证幂等？

**分三层看：稳定键（已有）、顺序保护（缺）、终态收敛（缺）——v4 只做对了第一层，而且连调用方都没接。**

1. **第一层：稳定键 + 幂等原语（✅ 做对）**
   - 删除消息只带 `documentId`，不描述「要删成什么样」，所以**重复执行结果相同**。
   - `es.delete({ index, id: documentId })` 对同一 `_id` 重复调用天然幂等。
   - **404 视为成功**：删一条不存在的文档不报错 —— 这是幂等删除的正确语义（`deleteDocument` 里 `if (!message.includes('404'))` 才 warn）。
   - `kh_chunk` 侧 `deleteByQuery({ term: { document_id } })` 同样幂等：命中 0 条也返回成功。
   - `refresh: true` 让删除立即可见，避免"删了但还能搜到"的窗口。
2. **第二层：顺序保护（❌ 缺）**
   - 没有 `version`：先发的 DELETE、后到的 INDEX（乱序/重投）会让**文档复活**。幂等只保证「同一操作重复执行结果相同」，不保证「不同操作按正确顺序生效」。
   - 补法：消息带 `version`；写入用 `if_seq_no`/`if_primary_term` 条件更新；或在 ES 文档里存 `version`，写脚本比较后 `noop`。
3. **第三层：终态收敛（❌ 缺）**
   - **`afterUnpublish()` 没有任何调用方**：`remove()` 只软删 PG + Mongo，不发事件 → `kh_document`/`kh_chunk` 里的记录永久残留。这是 v4 最严重的实际缺陷。
   - 归档（`PATCH status=2`）不更新 ES 的 `status`，改正文也不重建。
   - 补法：所有下线路径（删除/归档/改正文）都发事件；查询侧先用 `deleted`/`status` 过滤兜底（治标）；每小时对账 PG 文档集与 ES 文档集的差集，多删少补（治本）。
4. **还有一个"假成功"陷阱**：`deleteDocument` 吞掉非 404 异常后**无条件**打印「搜索索引已删除」。所以「幂等」和「成功」是两件事 —— 幂等的实现可能一直在失败，而日志说它成功了。**幂等 ≠ 可观测**。

> 一句话：**幂等靠稳定键做对了一半；但删除链路的真正风险不是"重复删"，而是"没人触发删"和"删错了没人知道"。**

## 12. 面试追问速答

1. **全文检索为什么不用 PG 的 `LIKE`/`tsvector`？**
   中文分词、BM25 相关性排序、高亮、海量数据下的倒排索引性能，ES 开箱即用；PG 做得好但要么上 `zhparser` 要么自己算相关性。既然 RAG 已经要 ES（`dense_vector`），同库同运维成本更低。
2. **为什么 `kh_document` 和 `kh_chunk` 不合成一个索引？**
   粒度不同（1:N）、成本不同（有无向量）、更新粒度不同、召回语义不同。合成一个索引会让「文档级排序」被块级数据污染，且向量存储白白放大到文档级。
3. **消息里带快照，正文改了怎么办？**
   当前是 bug（永久陈旧）。正解：`update()` 时也发 Search 事件（带新快照），或用 `version` + 消费时回查；或干脆改成「只带 ID + 版本号，消费时读 Mongo」。
4. **1000 字截断会不会漏召回？**
   会。这是「消息体积 vs 召回完整性」的显式取舍。若要全文可搜，让消费者按 ID 回查 Mongo（牺牲低依赖），或把正文存 OSS 由消费者取。
5. **ES 里 `content` 用默认分词有什么问题？**
   `standard` 对中文按单字切（"年假" → "年"、"假"），BM25 上相邻字词的相关性全丢。镜像已装 IK，需要 mapping 显式写 `analyzer: ik_max_word` / `search_analyzer: ik_smart`（且必须在建索引时就定，改 mapping 要 reindex）。
6. **为什么 `_id` 用 documentId 而不是自增？**
   幂等（同文档覆盖）、可直接按 ID 删/查、不需要额外维护 ID 映射。雪花 ID 转字符串避免 JS long 精度丢失。
7. **Search 消费失败会怎样？**
   异常冒泡 → `nack(requeue=false)` → 消息丢弃，无 DLQ、无重试、无状态记录。且成功也不 `ack`，所以 unacked 会堆积、重启后全量重投（重投无害，因为幂等）。
8. **怎么验证全文索引是对的？**
   `kh_document` 条数 = 已发布文档数（不是块数）；`indexedAt >= publishTime`；重复发布条数不变；`content` 长度 ≤ 1000；删除后应查不到（当前会查到 → 即缺陷）。
